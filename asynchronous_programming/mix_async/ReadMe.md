                            Future трейт.
Давайте начнём с более подробного изучения того, как работает трейт 
Future. Вот как он определяется в Rust:

use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

Это определение trait включает в себя ряд новых типов, а также некоторый 
синтаксис, которого мы раньше не видели, поэтому давайте рассмотрим 
определение по частям.

Во-первых, ассоциированный тип Future Output сообщает, во что разрешается
future. Это аналогично ассоциированному типу Item для типажа
Iterator. Во-вторых, у Future также есть метод poll, который принимает 
специальную ссылку Pin в качестве параметра self и изменяемую ссылку на 
тип Context, и возвращает Poll<Self::Output>. Мы подробнее поговорим о Pin
и Context чуть позже. А пока сосредоточимся на том, что возвращает метод,
— в типе Poll:

enum Poll<T> {
    Ready(T),
    Pending,
}

Этот тип опроса похож на Option. У него есть один вариант со значением 
Ready(T) и один без значения Pending. Однако Poll означает нечто 
совершенно иное, чем Option! Вариант Pending указывает на то, что будущий
объект ещё имеет работу чтобы делать, поэтому вызывающему потребуется 
повторить проверку позже. Вариант Ready указывает на то, что будущий 
объект завершил свою работу и значение T доступно.

Примечание: Для большинства futures вызывающий не должен повторно 
вызывать опрос после того, как future вернул состояние готовности. Многие 
futures перейдут в режим паники при повторном опросе после того, как они 
стали готовы. Для фьючерсов, которые можно безопасно опрашивать повторно,
это явно указано в документации. Это похоже на поведение Iterator::next.

Когда вы видите код, использующий await, Rust компилирует его в код, 
вызывающий poll. Если вы вернётесь к листингу 17-4, где мы вывели 
заголовок страницы для одного URL после его разрешения, Rust компилирует 
его примерно так (хотя и не совсем):

match page_title(url).poll() {
    Ready(page_title) => match page_title {
        Some(title) => println!("The title for {url} was {title}"),
        None => println!("{url} had no title"),
    }
    Pending => {
        // But what goes here?
    }
}

Что делать, когда будущее всё ещё в ожидании? Нам нужен способ пробовать
снова, снова и снова, пока будущее наконец не будет готово. Другими 
словами, нам нужен цикл:

let mut page_title_fut = page_title(url);
loop {
    match page_title_fut.poll() {
        Ready(value) => match page_title {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
        Pending => {
            // continue
        }
    }
}

Однако если бы Rust скомпилировал его именно в этот код, каждое ожидание 
было бы блокирующим — полная противоположность тому, к чему мы стремились!
Вместо этого Rust гарантирует, что цикл может передать управление чему-то,
что может приостановить работу над этим будущим, чтобы выполнить работу 
над другими будущими, а затем снова проверить этот. Как мы видели, этим 
чем-то является асинхронная среда выполнения, и эта работа по планированию
и координации — одна из её основных задач.

Ранее в этой главе мы описали ожидание rx.recv. Вызов recv возвращает 
future, а ожидание future опрашивает его. Мы отметили, что среда 
выполнения приостанавливает future до тех пор, пока он не будет готов, с 
помощью Some(message) или None при закрытии канала. Благодаря нашему 
более глубокому пониманию трейта Future, и в частности Future::poll, мы 
можем понять, как это работает. Среда выполнения знает, что future не 
готов, когда возвращает Poll::Pending. И наоборот, среда выполнения знает,
что future готов, и продвигает его, когда poll возвращает 
Poll::Ready(Some(message)) или Poll::Ready(None).

Точные детали того, как среда выполнения это делает, выходят за рамки 
этой книги, но главное — увидеть базовую механику будущих событий: среда 
выполнения опрашивает каждое будущее, за которое она отвечает, и переводит
будущее в спящий режим, когда оно еще не готово.


                        The Pin and Unpin Traits

очень неприятным сообщением об ошибке. Вот его соответствующая часть ещё 
раз:

Это сообщение об ошибке сообщает нам не только о необходимости закрепить 
значения, но и о причине этого закрепления. Функция trpl::join_all 
возвращает структуру JoinAll. Эта структура является обобщённой для типа 
F, который ограничен реализацией трейта Future. Непосредственное ожидание
будущего с помощью await неявно закрепляет будущее. Поэтому нам не нужно 
использовать pin! везде, где мы хотим ожидать будущее.

Однако здесь мы не ожидаем будущего напрямую. Вместо этого мы создаём 
новый будущий объект JoinAll, передавая коллекцию будущих объектов 
функции join_all. Сигнатура join_all требует, чтобы все типы элементов в 
коллекции реализовывали черту Future, а Box<T> реализует Future только в 
том случае, если обёрнутый им T является Future, реализующим 
черту Unpin.

Это очень сложно усвоить! Чтобы по-настоящему разобраться, давайте немного
углубимся в то, как работает trait Future, в частности, в вопросе 
закрепления.

Еще раз взглянем на определение trait Future :

use std::pin::Pin;
use std::task::{Context, Poll};

pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}


Параметр cx и его тип Context — ключ к тому, как среда выполнения 
фактически определяет, когда следует проверять заданный future-объект, 
сохраняя при этом ленивость. Опять же, подробности того, как это работает,
выходят за рамки этой главы, и, как правило, вам нужно учитывать это 
только при написании собственной реализации Future. Вместо этого мы 
сосредоточимся на типе для self, поскольку это первый случай, когда мы 
видим метод, где self имеет аннотацию типа. Аннотации типа для self 
работают так же, как аннотации типа для других параметров функции, но с 
двумя ключевыми отличиями:

a) Он сообщает Rust, какой тип self должен быть для вызова метода.
b) Это не может быть какой угодно тип. Он ограничен типом, для которого 
    реализован метод, ссылкой или умным указателем на этот тип, и (или)
    Pin-объектом, обёртывающим ссылку на этот тип.

Мы подробнее рассмотрим этот синтаксис в главе 18. На данный момент 
достаточно знать, что если мы хотим опросить future-объект, чтобы 
проверить, находится ли он в состоянии Pending или Ready(Output), нам 
нужна изменяемая ссылка на тип, заключенная в Pin-элемент.

Pin — это обёртка для типов, подобных указателям, таких как &, &mut, Box 
и Rc. (Технически Pin работает с типами, которые реализуют черты Deref 
или DerefMut, но это фактически эквивалентно работе только с указателями.)
Pin сам по себе не является указателем и не имеет собственного поведения,
в отличие от Rc и Arc в отношении подсчёта ссылок; это всего лишь
инструмент, который компилятор может использовать для обеспечения 
ограничений на использование указателей.

Напоминание о том, что await реализован в терминах вызовов poll, начинает
объяснять сообщение об ошибке, которое мы видели ранее, но оно было 
связано с Unpin, а не с Pin. Так как же Pin соотносится с Unpin, и почему
Future должен иметь тип Pin для вызова poll?

Помните, ранее в этой главе мы рассматривали последовательность точек 
ожидания в будущем, которые компилируются в конечный автомат, и компилятор
следит за тем, чтобы этот конечный автомат соответствовал всем стандартным
правилам Rust в отношении безопасности, включая заимствования и владение.
Чтобы это работало, Rust проверяет, какие данные необходимы между одной
точкой ожидания и либо следующей точкой ожидания, либо концом асинхронного
блока. Затем он создаёт соответствующий вариант в скомпилированном 
конечном автомате. Каждый вариант получает необходимый доступ к данным, 
которые будут использоваться в этом разделе исходного кода, либо путём 
получения права владения этими данными, либо путём получения изменяемой 
или неизменяемой ссылки на них.

Пока всё хорошо: если мы ошибёмся с владением или ссылками в данном 
асинхронном блоке, проверка заимствований сообщит нам об этом. Когда же 
нам нужно переместить future, соответствующую этому блоку, 
например, переместить её в Vec для передачи в join_all, всё становится 
сложнее.

Когда мы перемещаем будущий объект — будь то помещение его в структуру 
данных для использования в качестве итератора с join_all или возврат из 
функции — это фактически означает перемещение конечного автомата, 
создаваемого Rust. И, в отличие от большинства других типов в Rust, 
будущие объекты, создаваемые Rust для асинхронных блоков, могут содержать
ссылки на себя в полях любого заданного варианта, как показано на 
упрощённой иллюстрации на рисунке 17-4.

+-----+
|  1  | <-+

Однако по умолчанию любой объект, ссылающийся на себя, небезопасно 
перемещать, поскольку ссылки всегда указывают на фактический адрес памяти
того, на что они ссылаются (см. рис. 17-5). Если переместить саму 
структуру данных, эти внутренние ссылки останутся указывать на старое 
местоположение. Однако это местоположение в памяти теперь недействительно.
Во-первых, его значение не будет обновляться при внесении изменений в 
структуру данных. Во-вторых, что более важно, компьютер теперь может 
свободно использовать эту память для других целей! В конечном итоге вы 
можете прочитать совершенно не связанные данные.

+-----+             +-----+
|  ?  |             |  0  |
+-----+             +-----+
|  ?  |<--+         |  1  |
+-----+   |         +-----+
|     |   +-------- |     |
+-----+             +-----+

Рисунок 17-5: Небезопасный результат перемещения самореферентного типа 
              данных

Теоретически компилятор Rust мог бы попытаться обновить каждую ссылку на 
объект при его перемещении, но это может существенно снизить
производительность, особенно если требуется обновление целой сети ссылок.
Если бы мы могли гарантировать, что рассматриваемая структура данных не
перемещается в памяти, нам не пришлось бы обновлять ссылки. Именно этого 
требует функция проверки заимствований Rust: в безопасном коде она 
предотвращает перемещение любого элемента, на который есть активная 
ссылка.

Pin основан на этом, обеспечивая именно ту гарантию, которая нам нужна. 
Когда мы закрепляем значение, помещая указатель на него в Pin, оно больше
не может перемещаться. Таким образом, если у вас есть Pin<Box<SomeType>>,
вы фактически закрепляете значение SomeType, а не указатель на Box. 
Рисунок 17-6 иллюстрирует этот процесс.

                |  +-+    |
Pin -> b1 ------+->|0|    |

                |  | |<-+ |

На самом деле, указатель Box по-прежнему может свободно перемещаться. 
Помните: нам важно, чтобы данные, на которые он ссылается, оставались на 
месте. Если указатель перемещается, но данные, на которые он указывает, 
остаются на том же месте, как на рисунке 17-7, потенциальной проблемы нет.

а также модуль std::pin и попробуйте понять, как это сделать с Pin, 
обёртывающим Box. Суть в том, что сам самоссылающийся тип не может 
перемещаться, поскольку он по-прежнему закреплён.

Однако большинство типов совершенно безопасно перемещать, даже если они 
находятся за обёрткой Pin. Нам нужно думать о закреплении только тогда, 
когда у элементов есть внутренние ссылки. Примитивные значения, такие как 
числа и логические значения, безопасны, поскольку у них, очевидно, нет 
внутренних ссылок. Как и большинство типов, с которыми вы обычно работаете
в Rust. Например, вы можете перемещать Vec без беспокойства. Учитывая 
только то, что мы видели до сих пор, если у вас есть Pin<Vec<String>>, вам
придётся делать всё через безопасные, но ограниченные API, предоставляемые
Pin, хотя Vec<String> всегда безопасно перемещать, если на него нет других 
ссылок. Нам нужен способ сообщить компилятору, что в таких случаях можно 
перемещать элементы, — и вот тут-то в игру вступает Unpin.

Unpin — это trait-маркер, аналогичная traits Send и Sync, рассмотренным в
главе 16, и, следовательно, не имеющая собственной функциональности. 
Trait-маркеры существуют только для того, чтобы сообщить компилятору, что
тип, реализующий данную черту, можно безопасно использовать в определённом
контексте. Unpin сообщает компилятору, что данный тип не обязан 
предоставлять какие-либо гарантии относительно возможности безопасного 
перемещения рассматриваемого значения.

Как и в случае с Send и Sync, компилятор автоматически реализует Unpin 
для всех типов, для которых он может доказать их безопасность. Особый 
случай, опять же аналогичный Send и Sync, — это когда Unpin для типа не 
реализован. Это обозначается как impl !Unpin для SomeType, где 
SomeType — имя типа, который должен поддерживать эти гарантии безопасности
при использовании указателя на этот тип в Pin.

Другими словами, о связи между Pin и Unpin следует помнить два момента. 
Во-первых, Unpin — это «нормальный» случай, а !Unpin — особый. 
Во-вторых, то, реализует ли тип Unpin или !Unpin, имеет значение только 
при использовании закреплённого указателя на этот тип, например, 
Pin<&mut SomeType>.

Чтобы конкретнее представить себе строку: у неё есть длина и символы 
Unicode, из которых она состоит. Мы можем заключить строку в Pin, как 
показано на рисунке 17-8. Однако String автоматически реализует Unpin, 
как и большинство других типов в Rust.

       +--------------+
       | String       |
Pin -> + 5usize hello +
       +--------------+

Рисунок 17-8: Закрепление `String`; пунктирная линия указывает, что 
              `String` реализует черту `Unpin` и, таким образом, не 
              закрепляется.

В результате мы можем делать то, что было бы недопустимо, если бы String 
реализовал !Unpin, например, заменять одну строку другой в том же месте 
памяти, что и на рисунке 17-9. Это не нарушает контракт Pin, поскольку у 
String нет внутренних ссылок, которые делают перемещение по ней 
небезопасным! Именно поэтому он реализует Unpin, а не !Unpin.

       +----------------+
       | String         |
       | s2             |
Pin -> + 7usize goodbye +
       +----------------+

s1
5usize hello       

Рисунок 17-9: Замена `String` на совершенно другую `String` в памяти.

Теперь мы знаем достаточно, чтобы понять ошибки, обнаруженные для вызова 
join_all из листинга 17-17. Изначально мы пытались переместить будущие 
объекты, созданные асинхронными блоками, 
в Vec<Box<dyn Future<Output = ()>>>, но, как мы видели, эти будущие 
объекты могут иметь внутренние ссылки, поэтому они не реализуют Unpin. 
Их необходимо закрепить, и тогда мы можем передать тип Pin в Vec, будучи 
уверенными, что базовые данные в будущих объектах не будут перемещены.

Закрепление и открепление в основном важны для сборки низкоуровневых 
библиотек или самой среды выполнения, а не для повседневного кода Rust. 
Однако, когда вы видите эти признаки в сообщениях об ошибках, вы лучше 
понимаете, как исправить свой код!

Примечание: сочетание Pin и Unpin позволяет безопасно реализовать целый 
класс сложных типов в Rust, что в противном случае было бы сложно из-за 
самоссылаемости. Типы, требующие Pin, чаще всего встречаются в 
асинхронном Rust сегодня, но время от времени вы можете встретить их и в 
других контекстах.

Подробности работы Pin и Unpin, а также правила, которые они должны
соблюдать, подробно описаны в документации API для std::pin, поэтому, 
если вам интересно узнать больше, это отличное место для начала.

Если вы хотите еще более подробно понять, как все работает «под капотом», 
см. главы 2 и 4 книги «Асинхронное программирование в Rust»
https://rust-lang.github.io/async-book/
.

                            The Stream Trait
Теперь, когда вы более глубоко разобрались с типами Future, Pin и Unpin, 
мы можем перейти к типу Stream. Как вы узнали ранее в этой главе, потоки 
похожи на асинхронные итераторы. Однако, в отличие от Iterator и Future,
на момент написания этой статьи у Stream нет определения в стандартной
библиотеке, но есть очень распространённое определение из контейнера 
futures, используемого в экосистеме.

Давайте рассмотрим определения трейтов Iterator и Future, прежде чем 
рассматривать, как трейт Stream может их объединить. Iterator представляет
собой последовательность: его метод next предоставляет Option<Self::Item>.
Future представляет собой готовность с течением времени: его метод poll 
предоставляет Poll<Self::Output>. Чтобы представить последовательность 
элементов, которые становятся готовыми с течением времени, мы определяем 
трейт Stream, который объединяет эти свойства:

use std::pin::Pin;
use std::task::{Context, Poll};

trait Stream {
    type Item;

    fn poll_next(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>
    ) -> Poll<Option<Self::Item>>;
}

Трейт Stream определяет связанный тип, называемый Item, для типа элементов,
создаваемых потоком. Это похоже на Iterator, где может быть от нуля до
множества элементов, и в отличие от Future, где всегда есть один выход,
даже если это unit type ().

Stream также определяет метод для получения этих элементов. Мы называем 
его poll_next, чтобы было понятно, что он опрашивает так же, как 
Future::poll, и создаёт последовательность элементов так же, как 
Iterator::next. Его возвращаемый тип представляет собой комбинацию 
Poll и Option. Внешний тип — Poll, поскольку он должен проверяться на 
готовность, как это делает Future. Внутренний тип — Option, поскольку он
должен сообщать о наличии других сообщений, как это делает итератор.

Что-то очень похожее на это определение, вероятно, в конечном итоге 
войдет в стандартную библиотеку Rust. Пока же оно входит в набор 
инструментов большинства сред выполнения, так что вы можете на него 
положиться, и всё, что мы рассмотрим далее, в целом применимо!

Однако в примере, который мы рассматривали в разделе о потоковой передаче,
мы использовали не poll_next или Stream, а next и StreamExt. Конечно, мы 
могли бы работать напрямую с API poll_next, вручную написав собственные 
конечные автоматы Stream, точно так же, как мы могли бы работать с 
фьючерсами напрямую через их метод poll. Однако использование await 
гораздо удобнее, а тип StreamExt предоставляет метод next, так что мы 
можем сделать именно это:

trait StreamExt: Stream {
    async fn next(&mut self) -> Option<Self::Item>
    where
        Self: Unpin;

    // other methods...
}

Примечание: Фактическое определение, которое мы использовали ранее в этой
главе, выглядит несколько иначе, поскольку оно поддерживает версии Rust,
которые ещё не поддерживали использование асинхронных функций в трейтах.
В результате оно выглядит так:

fn next(&mut self) -> Next<'_, Self> where Self: Unpin;

Этот тип Next представляет собой структуру, которая реализует Future и
позволяет нам называть время жизни ссылки на себя с помощью Next<'_, Self>,
чтобы await мог работать с этим методом.

Трейт StreamExt также является домом для всех интересных методов, 
доступных для использования с потоками. StreamExt автоматически 
реализуется для каждого типа, реализующего Stream, но эти трейты 
определяются отдельно, чтобы сообщество могло дорабатывать удобные API, 
не затрагивая базовый трейт.

В версии StreamExt, используемой в контейнере trpl, этот тип не только 
определяет метод next, но и предоставляет реализацию next по умолчанию, 
которая корректно обрабатывает детали вызова Stream::poll_next. Это 
означает, что даже если вам нужно написать собственный потоковый тип 
данных, вам достаточно реализовать только Stream, и тогда любой, кто 
использует ваш тип данных, сможет автоматически использовать StreamExt и 
его методы.

Это всё, что мы собираемся рассмотреть в общих чертах по этим 
характеристикам. В заключение давайте рассмотрим, как сочетаются между 
собой фьючерсы (включая потоки), задачи и потоки!
