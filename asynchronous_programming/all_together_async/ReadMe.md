Как мы видели в главе 16
https://doc.rust-lang.org/stable/book/ch16-00-concurrency.html
, потоки предоставляют один из подходов к параллельной обработке. В этой
главе мы рассмотрели другой подход: использование асинхронности с 
фьючерсами и потоками. Если вы задаетесь вопросом, когда выбрать метод, а
когда — другой, ответ: всё зависит от обстоятельств! И во многих случаях 
выбор стоит не между потоками или асинхронностью, а между потоками и 
асинхронностью.

Многие операционные системы уже несколько десятилетий поддерживают модели
параллельного выполнения, основанные на потоках, и многие языки 
программирования поддерживают их. Однако эти модели не лишены недостатков.
Во многих операционных системах они используют значительный объём памяти
для каждого потока и требуют определённых накладных расходов на запуск и
завершение работы. Потоки также возможны только при условии их поддержки
операционной системой и оборудованием. В отличие от массовых настольных и
мобильных компьютеров, некоторые встраиваемые системы вообще не имеют ОС,
поэтому в них нет и потоков.

Асинхронная модель предлагает иной — и, в конечном счёте, 
взаимодополняющий — набор компромиссов. В асинхронной модели параллельные
операции не требуют собственных потоков. Вместо этого они могут
выполняться в задачах, как, например, когда мы использовали 
trpl::spawn_task для запуска работы синхронной функции в разделе потоков.
Задача похожа на поток, но вместо управления операционной системой она 
управляется кодом уровня библиотеки: средой выполнения.

В предыдущем разделе мы увидели, что можно создать поток, используя 
асинхронный канал и создав асинхронную задачу, которую можно вызвать из 
синхронного кода. То же самое можно сделать и с потоком. В листинге 
17-40 мы использовали trpl::spawn_task и trpl::sleep. В листинге 17-41 
мы заменяем их API-функциями thread::spawn и thread::sleep из стандартной
библиотеки в функции get_intervals.

Имя файла: src/main.rs

```rust
fn get_intervals() -> impl Stream<Item = u32> {
    let (tx, rx) = trpl::channel();

    // This is *not* `trpl::spawn` but `std::thread::spawn`!
    thread::spawn(move || {
        let mut count = 0;
        loop {
            // Likewise, this is *not* `trpl::sleep` but `std::thread::sleep`!
            thread::sleep(Duration::from_millis(1));
            count += 1;

            if let Err(send_error) = tx.send(count) {
                eprintln!("Could not send interval {count}: {send_error}");
                break;
            };
        }
    });

    ReceiverStream::new(rx)
}
```

Листинг 17-41: Использование API std::thread вместо API async trpl для 
               функции get_intervals

Если запустить этот код, вывод будет идентичен выводу из листинга 17-40. 
Обратите внимание, как мало изменений произошло с точки зрения вызывающего
кода. Более того, хотя одна из наших функций породила асинхронную задачу 
в среде выполнения, а другая — поток ОС, эти различия не повлияли на 
результирующие потоки.

Несмотря на сходство, эти два подхода ведут себя совершенно по-разному, 
хотя нам может быть сложно оценить это на этом очень простом примере. На 
любом современном персональном компьютере можно было бы создать миллионы
асинхронных задач. Если бы мы попытались сделать это с помощью потоков, у
нас бы буквально закончилась память!

Однако есть причина, по которой эти API так похожи. Потоки служат 
границей для наборов синхронных операций; между потоками возможен 
параллелизм. Задачи служат границей для наборов асинхронных операций; 
параллелизм возможен как между задачами, так и внутри них, поскольку 
задача может переключаться между будущими задачами в своём теле. Наконец,
будущие задачи — наиболее гранулярная единица параллелизма в Rust, и 
каждый будущий процесс может представлять собой дерево других будущих 
процессов. Среда выполнения, а именно её исполнитель, управляет задачами,
а задачи управляют будущими процессами. В этом отношении задачи похожи на
облегчённые потоки, управляемые средой выполнения, с дополнительными 
возможностями, которые возникают благодаря управлению средой выполнения,
а не операционной системой.

Это не означает, что асинхронные задачи всегда лучше потоков 
(или наоборот). Параллелизм с потоками в некотором смысле является более 
простой моделью программирования, чем параллелизм с асинхронностью. Это
может быть как преимуществом, так и недостатком. Потоки работают по 
принципу «запустил и забыл»; у них нет встроенного эквивалента фьючерса,
поэтому они просто выполняются до завершения, не прерываясь ничем, кроме
самой операционной системы. То есть, у них нет встроенной поддержки 
внутризадачного параллелизма, как это делают фьючерсы. У потоков в Rust 
также нет механизмов отмены — тема, которую мы явно не рассматривали в 
этой главе, но которая подразумевалась тем фактом, что при завершении 
фьючерса его состояние корректно очищалось.

Эти ограничения также усложняют компоновку потоков по сравнению с 
фьючерсами. Например, гораздо сложнее использовать потоки для создания 
вспомогательных функций, таких как методы timeout и throttle, которые мы 
создали ранее в этой главе. Тот факт, что фьючерсы представляют собой 
более содержательные структуры данных, означает, что их можно компоновать
более естественно, как мы уже видели.

Таким образом, задачи дают нам дополнительный контроль над будущими 
задачами, позволяя выбирать, где и как их группировать. И оказывается, 
что потоки и задачи часто отлично работают вместе, поскольку задачи можно
(по крайней мере, в некоторых средах выполнения) перемещать между 
потоками. Фактически, используемая нами среда выполнения, включая функции
spawn_blocking и spawn_task, по умолчанию многопоточная! Многие среды 
выполнения используют подход, называемый «перехватом работы», для 
прозрачного перемещения задач между потоками в зависимости от того, как 
эти потоки используются в данный момент, чтобы повысить общую 
производительность системы. Этот подход фактически требует потоков и 
задач, а следовательно, и будущих задач.

Размышляя о том, какой метод и когда использовать, примите во внимание
следующие практические правила:

a) Если работа легко поддается распараллеливанию, например, обработка 
   большого объема данных, где каждая часть может быть обработана 
   отдельно, то потоки являются лучшим выбором.

b) Если работа носит многопараллельный характер, например, обработка 
   сообщений из множества разных источников, которые могут поступать с 
   разными интервалами или с разной скоростью, лучшим выбором будет 
   асинхронный режим.

А если вам нужны и параллелизм, и конкурентность, вам не придётся 
выбирать между потоками и асинхронностью. Вы можете свободно использовать
их вместе, позволяя каждому из них выполнять свою функцию. Например, в 
листинге 17-42 показан довольно распространённый пример такого сочетания в
реальном коде Rust.

Имя файла: src/main.rs

```rust
use std::{thread, time::Duration};

fn main() {
    let (tx, mut rx) = trpl::channel();

    thread::spawn(move || {
        for i in 1..11 {
            tx.send(i).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    trpl::run(async {
        while let Some(message) = rx.recv().await {
            println!("{message}");
        }
    });
}
```

Листинг 17-42: Отправка сообщений с блокирующим кодом в потоке и ожидание
               сообщений в асинхронном блоке

Мы начинаем с создания асинхронного канала, затем создаём поток, который 
берёт на себя управление отправителем канала. Внутри этого потока мы 
отправляем числа от 1 до 10, делая паузу в секунду между каждым. Наконец,
мы запускаем будущий поток, созданный с помощью асинхронного блока, 
переданного в trpl::run, как и на протяжении всей главы. В этом будущем 
мы ожидаем эти сообщения, как и в других рассмотренных нами примерах 
передачи сообщений.

Возвращаясь к сценарию, с которого мы начали главу, представьте, что вы 
запускаете набор задач кодирования видео, используя выделенный поток 
(поскольку кодирование видео ограничено вычислительными ресурсами), но 
при этом уведомляете пользовательский интерфейс о том, что эти операции 
выполняются по асинхронному каналу. В реальных сценариях использования 
существует множество примеров подобных комбинаций.
