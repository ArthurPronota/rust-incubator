Это определённо лучше, чем подстановка join в join3, join4 и так далее!

Мы можем использовать trpl::join! для их ожидания, поскольку он позволяет
передавать несколько типов будущих событий и возвращает кортеж этих типов.
Мы не можем использовать trpl::join_all, поскольку он требует, чтобы все 
переданные будущие события имели один и тот же тип. Помните, именно эта

Это фундаментальный компромисс: мы можем либо работать с динамическим 
количеством фьючерсов с помощью join_all, при условии, что все они имеют 
один и тот же тип, либо работать с фиксированным количеством фьючерсов с 
помощью функций join или макроса join!, даже если у них разные типы. С 
этим же сценарием мы сталкиваемся при работе с любыми другими типами в 
Rust. Фьючерсы не являются чем-то особенным, хотя у нас есть удобный 
синтаксис для работы с ними, и это хорошо.

                            Гонки Futures
Когда мы «соединяем» futures объекты с помощью семейства функций и 
макросов join, мы требуем, чтобы все они были завершены, прежде чем 
двигаться дальше. Однако иногда нам нужно завершить только какой-то 
future из набора, прежде чем двигаться дальше — это похоже на гонку между
двумя future объектами.

В листинге 17-21 мы снова используем trpl::race для сравнения двух 
futures, медленного и быстрого.

Имя файла: src/main.rs

        let slow = async {
            println!("'slow' started.");
            trpl::sleep(Duration::from_millis(100)).await;
            println!("'slow' finished.");
        };

        let fast = async {
            println!("'fast' started.");
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'fast' finished.");
        };

        trpl::race(slow, fast).await;

Листинг 17-21: Использование race для получения результата того, какой 
               будущий процесс завершится первым

Каждый future выводит сообщение при запуске, приостанавливается на 
некоторое время, вызывая и ожидая sleep, а затем выводит другое сообщение
по завершении. Затем мы передаём оба значения slow и fast в trpl::race и 
ждём завершения одного из них. (Результат здесь не слишком удивителен: 
побеждает fast.) В отличие от использования race в 
«Нашей первой асинхронной программе», здесь мы просто игнорируем 
возвращаемый им экземпляр Either, потому что всё интересное поведение 
происходит в теле асинхронных блоков.

Обратите внимание, что если изменить порядок аргументов на race, порядок
сообщений «started» изменится, хотя быстрый future всегда завершается
первым. Это связано с тем, что реализация этой конкретной функции race 
несправедлива. Она всегда запускает future-объекты, переданные в 
качестве аргументов, в том порядке, в котором они были переданы. Другие
реализации справедливы и случайным образом выбирают, какой future-объект 
опрашивать первым. Однако независимо от того, справедлива ли используемая
нами реализация race, один из future-объектов достигнет первого await в 
своём теле, прежде чем сможет начаться другая задача.

Вспомните «Нашу первую асинхронную программу», что в каждой точке 
await Rust даёт среде выполнения возможность приостановить задачу и 
переключиться на другую, если ожидаемое будущее не готово. Обратное также
верно: Rust приостанавливает асинхронные блоки и возвращает управление
среде выполнения только в точке ожидания. Всё между точками ожидания 
синхронно.

Это означает, что если вы выполняете много работы в асинхронном блоке без
await точки, этот future объект заблокирует выполнение всех других 
future объектов. Иногда это можно услышать как 
«один будущий объект истощает другие будущие объекты». В некоторых случаях
это может быть не так уж и важно. Однако, если вы выполняете какую-то 
дорогостоящую настройку или длительную работу, или если у вас есть 
будущий объект, который будет выполнять какую-то конкретную задачу 
бесконечно, вам нужно подумать о том, когда и где вернуть управление 
среде выполнения.

Подобным же образом, если у вас есть длительные блокирующие операции, 
async может быть полезным инструментом для предоставления способов 
взаимодействия между различными частями программы.

Но как в таких случаях вернуть управление среде выполнения?

                    Уступая управления среде выполнения
Давайте смоделируем длительную операцию. В листинге 17-22 представлена 
​​медленная функция.

fn slow(name: &str, ms: u64) {
    thread::sleep(Duration::from_millis(ms));
    println!("'{name}' ran for {ms}ms");
}

Листинг 17-22: Использование thread::sleep для имитации медленных операций

В этом коде используется std::thread::sleep вместо trpl::sleep, поэтому 
вызов slow блокирует текущий поток на некоторое количество миллисекунд. 
Мы можем использовать slow для реальных операций, которые одновременно 
являются длительными и блокирующими.

В листинге 17-23 мы используем slow для эмуляции выполнения такого рода
работы, связанной с процессором, в паре futures.

Имя файла: src/main.rs

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            slow("a", 10);
            slow("a", 20);
            trpl::sleep(Duration::from_millis(50)).await;
            println!("'a' finished.");

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            slow("b", 10);
            slow("b", 15);

Начнем с того, что каждый будущий объект возвращает управление среде 
выполнения только после выполнения ряда медленных операций. Если запустить
этот код, вы увидите следующий вывод:

'a' ran for 10ms
'a' ran for 20ms
'b' started.

Как и в нашем предыдущем примере, гонка по-прежнему завершается, как 
только завершается "a". Однако между двумя futures нет чередования. 
Future задача "a" выполняет всю свою работу до тех пор, пока не будет 
ожидание вызова trpl::sleep, затем future "b" выполняет всю свою работу 
до тех пор, пока не будет ожидание его собственного вызова trpl::sleep, и,
наконец, future "a" завершается. Чтобы оба futures могли выполняться 
между своими медленными задачами, нам нужны точки ожидания, чтобы мы 
могли вернуть управление среде выполнения. Это значит, что нам нужно 
что-то, что мы можем ожидать!

Мы уже видим подобную передачу управления в листинге 17-23: если бы мы 
удалили trpl::sleep в конце future "a", оно бы завершилось без запуска 
future "b". Попробуем использовать функцию sleep в качестве отправной 
точки для остановки операций в процессе выполнения, как показано в 
листинге 17-24.

Имя файла: src/main.rs

        let one_ms = Duration::from_millis(1);

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::sleep(one_ms).await;
            slow("a", 10);
            trpl::sleep(one_ms).await;
            slow("a", 20);
            trpl::sleep(one_ms).await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::sleep(one_ms).await;
            slow("b", 10);
            trpl::sleep(one_ms).await;
            slow("b", 15);
            trpl::sleep(one_ms).await;
            slow("b", 350);
            trpl::sleep(one_ms).await;
            println!("'b' finished.");
        };

Листинг 17-24: Использование сна для остановки операций в процессе 
               выполнения

В листинге 17-24 мы добавляем вызовы trpl::sleep с точками ожидания между
каждым вызовом, чтобы замедлить выполнение. Теперь работа двух фьючерсов 
чередуется:

'a' started.
'a' ran for 30ms
'b' started.
'b' ran for 75ms
'a' ran for 10ms
'b' ran for 10ms
'a' ran for 20ms
'b' ran for 15ms
'a' finished.

Futures "a" всё ещё выполняется некоторое время, прежде чем передать 
управление "b", поскольку он вызывает slow перед вызовом trpl::sleep, но 
после этого фьючерсы меняются местами каждый раз, когда один из них 
достигает точки ожидания. В данном случае мы делали это после каждого 
вызова slow, но мы можем разделить работу любым удобным для нас способом.

Но на самом деле мы не хотим здесь спать: мы хотим двигаться вперёд как 
можно быстрее. Нам просто нужно вернуть управление среде выполнения. Это 
можно сделать напрямую, используя функцию yield_now. В листинге 17-25 мы 
заменяем все эти вызовы sleep на yield_now.

Имя файла: src/main.rs

        let a = async {
            println!("'a' started.");
            slow("a", 30);
            trpl::yield_now().await;
            slow("a", 10);
            trpl::yield_now().await;
            slow("a", 20);
            trpl::yield_now().await;
            println!("'a' finished.");
        };

        let b = async {
            println!("'b' started.");
            slow("b", 75);
            trpl::yield_now().await;
            slow("b", 10);
            trpl::yield_now().await;
            slow("b", 15);
            trpl::yield_now().await;
            slow("b", 350);
            trpl::yield_now().await;
            println!("'b' finished.");
        };

Листинг 17-25: Использование yield_now для остановки операций в процессе 
               выполнения

Этот код яснее отражает истинное намерение и может работать значительно 
быстрее, чем при использовании sleep, поскольку таймеры, подобные 
используемому в sleep, часто имеют ограничения по детализации. Например, 
используемая нами версия sleep всегда будет спать не менее миллисекунды, 
даже если мы передадим ей значение Duration в одну наносекунду. Опять же,
современные компьютеры быстры: они могут многое сделать за одну 
миллисекунду!

Вы можете убедиться в этом сами, создав небольшой тест производительности,
например, как в листинге 17-26. (Это не самый строгий способ тестирования
производительности, но его достаточно, чтобы продемонстрировать разницу.)

Имя файла: src/main.rs

        let one_ns = Duration::from_nanos(1);
        let start = Instant::now();
        async {
            for _ in 1..1000 {
                trpl::sleep(one_ns).await;
            }
        }
        .await;
        let time = Instant::now() - start;
        println!(
            "'sleep' version finished after {} seconds.",
            time.as_secs_f32()
        );

        let start = Instant::now();
        async {
            for _ in 1..1000 {
                trpl::yield_now().await;
            }
        }
        .await;
        let time = Instant::now() - start;
        println!(
            "'yield' version finished after {} seconds.",
            time.as_secs_f32()
        );

Листинг 17-26: Сравнение производительности sleep и yield_now

Здесь мы пропускаем вывод всех статусов, передаём длительность в одну 
наносекунду в trpl::sleep и позволяем каждому будущему выполняться 
самостоятельно, без переключения между ними. Затем мы запускаем 1000 
итераций и сравниваем время выполнения будущего с использованием 
trpl::sleep с временем выполнения будущего с использованием 
trpl::yield_now.


sleep vesion finished after: 131.16756 seconds.
yeld version finished after: 0.007346 seconds

Версия с yield_now намного быстрее!

Это означает, что асинхронность может быть полезна даже для задач, 
связанных с вычислительными ресурсами, в зависимости от того, что ещё 
делает ваша программа, поскольку она предоставляет полезный инструмент для
структурирования взаимосвязей между различными частями программы. Это 
форма кооперативной многозадачности, где каждый furure может определить, 
когда он передаёт управление, через точки ожидания. Таким образом, каждый
future также несёт ответственность за предотвращение слишком длительной 
блокировки. В некоторых встраиваемых операционных системах на базе Rust 
это единственный вид многозадачности!

В реальном коде, конечно, обычно не приходится чередовать вызовы функций с
точками ожидания в каждой строке. Хотя такая передача управления 
относительно недорога, она не бесплатна. Во многих случаях попытка разбить
задачу, связанную с вычислительными ресурсами, может значительно замедлить
её выполнение, поэтому иногда для общей производительности лучше позволить
операции ненадолго заблокироваться. Всегда измеряйте производительность, 
чтобы определить фактические узкие места вашего кода. Однако важно 
учитывать базовую динамику, если вы видите, что много работы выполняется 
последовательно, а вы ожидали, что она будет выполняться одновременно!

                    Создание собственных асинхронных абстракций
Мы также можем компоновать Futures для создания новых шаблонов. 
Например, мы можем создать функцию тайм-аута из уже имеющихся асинхронных
блоков. В результате получится ещё один блок, который можно использовать 
для создания ещё большего количества асинхронных абстракций.

В листинге 17–27 показано, как, по нашим ожиданиям, этот тайм-аут будет 
работать с медленным будущим.

Имя файла: src/main.rs

        let slow = async {
            trpl::sleep(Duration::from_millis(100)).await;
            "I finished!"
        };

        match timeout(slow, Duration::from_millis(10)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }

Листинг 17-27: Использование нашего воображаемого тайм-аута для выполнения
               медленной операции с ограничением по времени

Давайте реализуем это! Для начала давайте подумаем об API для тайм-аута:
a) Это должна быть асинхронная функция, чтобы мы могли ее ожидать.
b) Его первым параметром должен быть future, который нужно запустить. Мы 
    можем сделать его универсальным, чтобы он мог работать с любым 
    будущим объектом.
c) Вторым параметром будет максимальное время ожидания. Если мы 
    используем Duration, это упростит передачу в trpl::sleep.
d) Он должен вернуть Result. Если furure завершится успешно, результат 
    будет Ok со значением, полученным в результате. Если тайм-аут истечёт
    раньше, результат будет Err со значением, равным времени ожидания.

Листинг 17-28: Определение сигнатуры тайм-аута

Это удовлетворяет нашим требованиям к типам. Теперь давайте подумаем о 
необходимом поведении: мы хотим, чтобы переданное будущее зависело от 
длительности. Мы можем использовать trpl::sleep для создания будущего 
таймера на основе длительности и использовать trpl::race для запуска 
этого таймера с переданным вызывающим будущим.

Мы также знаем, что race нечестно опрашивать аргументы в порядке их 
передачи. Таким образом, мы передаём future_to_try в race первым, чтобы у
него был шанс завершиться, даже если max_time — очень короткое время. 
Если future_to_try завершится первым, race вернёт Left с выходными данными
future_to_try. Если timer завершится первым, race вернёт Right с 
выходными данными таймера ().

В листинге 17-29 мы сопоставляем результат ожидания trpl::race.

Имя файла: src/main.rs

use trpl::Either;

// --snip--

fn main() {
    trpl::run(async {
        let slow = async {
            trpl::sleep(Duration::from_secs(5)).await;
            "Finally finished"
        };

        match timeout(slow, Duration::from_secs(2)).await {
            Ok(message) => println!("Succeeded with '{message}'"),
            Err(duration) => {
                println!("Failed after {} seconds", duration.as_secs())
            }
        }
    });
}

async fn timeout<F: Future>(
    future_to_try: F,
    max_time: Duration,
) -> Result<F::Output, Duration> {
    match trpl::race(future_to_try, trpl::sleep(max_time)).await {
        Either::Left(output) => Ok(output),
        Either::Right(_) => Err(max_time),
    }


Листинг 17-29: Определение тайм-аута с учетом гонки и сна

Если future_to_try завершается успешно и мы получаем Left(output), мы 
возвращаем Ok(output). Если же таймер сна истекает и мы получаем Right(()),
мы игнорируем () с _ и возвращаем Err(max_time).

Таким образом, у нас есть работающий тайм-аут, построенный на основе двух
других асинхронных вспомогательных функций. Если мы запустим наш код, он 
выведет режим сбоя по истечении тайм-аута:

Failed after 2 seconds

Поскольку фьючерсы компонуются с другими фьючерсами, вы можете создавать 
действительно мощные инструменты, используя более мелкие асинхронные 
строительные блоки. Например, этот же подход можно использовать для 
объединения тайм-аутов с повторными попытками, а затем использовать их с 
такими операциями, как сетевые вызовы (один из примеров в начале главы).

На практике вы обычно работаете напрямую с async и await, а затем с
