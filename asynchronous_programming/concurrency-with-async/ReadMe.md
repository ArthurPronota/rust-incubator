[Применение конкуренции с помощью асинхронности](https://doc.rust-lang.org/stable/book/ch17-02-concurrency-with-async.html)

            
В этом разделе мы применим асинхронность к некоторым из тех же проблем 
параллелизма, которые мы решали с помощью потоков в главе 16. Поскольку 
мы уже обсудили многие ключевые идеи, в этом разделе мы сосредоточимся на
различиях между threads и futures.

Во многих случаях API для работы с concurrency с использованием 
асинхронности очень похожи на API для потоков. В других случаях они 
оказываются совершенно разными. Даже если API потоков и асинхронности 
выглядят похожими, они часто ведут себя по-разному, и почти всегда имеют 
разные характеристики производительности.

<h4>Создание новой задачи с помощью spawn_task</h4>

Первая операция, которую мы рассмотрели в разделе 
«Создание нового потока с помощью Spawn»
https://doc.rust-lang.org/stable/book/ch16-01-threads.html#creating-a-new-thread-with-spawn
, — это подсчёт в двух отдельных потоках. Давайте сделаем то же самое, 
используя асинхронный метод. Пакет trpl предоставляет функцию spawn_task,
очень похожую на API thread::spawn, и функцию sleep, представляющую собой
асинхронную версию API thread::sleep. Мы можем использовать их вместе
для реализации примера подсчёта, как показано в листинге 17-6.

Имя файла: src/main.rs

```rust
use std::time::Duration;

fn main() {
    trpl::run(async {
        trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }
    });
}
```

Листинг 17-6: Создание новой задачи для печати одной вещи, пока 
              основная задача печатает что-то другое

В качестве отправной точки мы настраиваем нашу основную функцию с помощью
trpl::run, чтобы наша функция верхнего уровня могла быть асинхронной.

Примечание: Начиная с этого момента в этой главе каждый пример будет 
включать тот же самый код обёртки с trpl::run в main, поэтому мы часто 
будем пропускать его, как и main. Не забудьте включить его в свой код!

Затем мы пишем два цикла внутри этого блока, каждый из которых содержит 
вызов trpl::sleep, который ожидает полсекунды (500 миллисекунд) перед 
отправкой следующего сообщения. Один цикл мы помещаем в тело 
trpl::spawn_task, а другой — в цикл for верхнего уровня. Мы также 
добавляем await после вызовов sleep.

Этот код ведет себя аналогично реализации на основе потоков, включая тот 
факт, что при запуске вы можете увидеть сообщения в другом порядке на 
своем терминале:

```text
hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
```

Эта версия останавливается сразу после завершения цикла for в теле 
основного асинхронного блока, поскольку задача, порождённая функцией 
spawn_task, завершается по завершении основной функции. Если вы хотите, 
чтобы она выполнялась до завершения задачи, вам потребуется использовать 
метод join для ожидания завершения первой задачи. В случае потоков мы 
использовали метод join для «блокировки» до завершения выполнения потока.
В листинге 17-7 мы можем использовать await для того же самого, поскольку
сам дескриптор задачи является будущим. Его типом Output является Result,
поэтому мы также разворачиваем его после ожидания.

Имя файла: src/main.rs

```rust
        let handle = trpl::spawn_task(async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }

        handle.await.unwrap();
```

Листинг 17-7: Использование await с join обработчиком для выполнения 
              задачи до завершения

Эта обновленная версия работает до тех пор, пока не завершатся оба цикла.

hi number 1 from the second task!
hi number 1 from the first task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

На данный момент похоже, что async и threads дают нам одинаковые базовые
результаты, просто с разным синтаксисом: использование await вместо 
вызова join на дескрипторе join и ожидание вызовов sleep.

Главное отличие заключается в том, что для этого нам не нужно было 
создавать ещё один поток операционной системы. Более того, нам даже не 
нужно создавать задачу. Поскольку асинхронные блоки компилируются в 
анонимные будущие объекты, мы можем поместить каждый цикл в асинхронный 
блок и заставить среду выполнения выполнить их оба до завершения с 
помощью функции trpl::join.

В разделе Ожидание завершения всех потоков с использованием дескрипторов 
соединений https://doc.rust-lang.org/stable/book/ch16-01-threads.html#waiting-for-all-threads-to-finish-using-join-handles
мы показали, как использовать метод join для типа JoinHandle, 
возвращаемого при вызове std::thread::spawn. Функция trpl::join похожа, 
но для фьючерсов. Когда вы передаете ей два фьючерса, она создает один 
новый фьючерс, выход которого представляет собой кортеж, содержащий выход
каждого переданного вами фьючерса, после их завершения. Таким образом, в 
листинге 17-8 мы используем trpl::join для ожидания завершения fut1 и 
fut2. Мы ждем не fut1 и fut2, а новый фьючерс, созданный trpl::join. Мы 
игнорируем этот вывод, потому что это просто кортеж, содержащий два 
unit значений.

Имя файла: src/main.rs

        let fut1 = async {
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let fut2 = async {
            for i in 1..5 {
                println!("hi number {i} from the second task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        trpl::join(fut1, fut2).await;

Листинг 17-8: Использование trpl::join для ожидания двух анонимных 
              будущих событий

При запуске мы видим, что оба будущих варианта выполняются до завершения:

hi number 1 from the first task!
hi number 1 from the second task!
hi number 2 from the first task!
hi number 2 from the second task!
hi number 3 from the first task!
hi number 3 from the second task!
hi number 4 from the first task!
hi number 4 from the second task!
hi number 5 from the first task!
hi number 6 from the first task!
hi number 7 from the first task!
hi number 8 from the first task!
hi number 9 from the first task!

Теперь вы будете видеть один и тот же порядок каждый раз, что сильно 
отличается от того, что мы видели с потоками. Это связано с тем, что 
функция trpl::join является справедливой, то есть она проверяет каждое 
будущее одинаково часто, чередуя их, и никогда не позволяет одному из них
вырваться вперед, если другой готов. С потоками операционная система 
решает, какой поток проверять и как долго ему позволять выполняться. В 
асинхронном Rust среда выполнения решает, какую задачу проверять. 
(На практике детали усложняются, поскольку асинхронная среда выполнения 
может использовать потоки операционной системы под капотом как часть того,
как она управляет параллелизмом, поэтому обеспечение справедливости может
быть более трудоемким для среды выполнения, но это все еще возможно!)
Среды выполнения не обязаны гарантировать справедливость для любой 
заданной операции, и они часто предлагают разные API, позволяющие вам 
выбирать, нужна ли вам справедливость или нет.

Попробуйте некоторые из этих вариантов ожидания будущего и посмотрите, 
что они дают:
a) Удалите асинхронный блок из одного или обоих циклов.
b) Ожидайте каждый асинхронный блок сразу после его определения.
c) Оберните только первый цикл в асинхронный блок и ждите результирующего
   future-события после тела второго цикла.

Для дополнительной сложности попробуйте определить, какой будет вывод в 
каждом случае, прежде чем запускать код!

            Подсчет двух задач с использованием передачи сообщений
Обмен данными между фьючерсами также будет вам знаком: мы снова 
воспользуемся передачей сообщений, но на этот раз с асинхронными версиями
типов и функций. Мы пойдём немного другим путём, чем в разделе 
«Использование передачи сообщений для передачи данных между потоками»
https://doc.rust-lang.org/stable/book/ch16-02-message-passing.html
, чтобы проиллюстрировать некоторые ключевые различия между параллельным 
выполнением на основе потоков и конкурентности. В листинге 17-9 мы начнём 
с одного асинхронного блока, не порождая отдельную задачу, как мы 
создавали отдельный поток.

Имя файла: src/main.rs

        let (tx, mut rx) = trpl::channel();

        let val = String::from("hi");
        tx.send(val).unwrap();

        let received = rx.recv().await.unwrap();
        println!("received '{received}'");

Листинг 17-9: Создание асинхронного канала и назначение двух его половин
              tx и rx

Здесь мы используем trpl::channel, асинхронную версию API канала с 
несколькими производителями и одним потребителем, который мы использовали
с потоками в главе 16. Асинхронная версия API лишь немного отличается от 
версии, основанной на потоках: она использует изменяемый, 
а не неизменяемый приёмник rx, а её метод recv создаёт future-объект, 
который нужно ожидать, а не выдавать значение напрямую. Теперь мы можем 
отправлять сообщения от отправителя получателю. Обратите внимание, 
что нам не нужно создавать отдельный поток или даже задачу; 
нам достаточно просто дождаться вызова rx.recv.

Синхронный метод Receiver::recv в std::mpsc::channel блокируется до 
получения сообщения. Метод trpl::Receiver::recv этого не делает, 
поскольку он асинхронный. Вместо блокировки он возвращает управление 
среде выполнения до тех пор, пока сообщение не будет получено или 
отправитель канала не закроется. В отличие от этого, мы не ожидаем 
вызова send, поскольку он не блокируется. Это и не нужно, поскольку 
канал, в который мы его отправляем, не имеет ограничений.

Примечание: Поскольку весь этот асинхронный код выполняется в асинхронном
блоке в вызове trpl::run, всё внутри него может избежать блокировки. 
Однако код за его пределами заблокируется при возврате функции run. В 
этом и заключается суть функции trpl::run: она позволяет выбрать, где 
блокировать определённый набор асинхронного кода, и, следовательно, где 
осуществлять переход между синхронным и асинхронным кодом. В большинстве 
асинхронных сред выполнения run на самом деле называется block_on именно 
по этой причине.

Обратите внимание на два момента в этом примере. Во-первых, сообщение 
придёт немедленно. Во-вторых, хотя мы используем здесь будущий объект, 
параллельность пока отсутствует. Всё в списке происходит последовательно,
как если бы не было никаких Futures.

Давайте рассмотрим первую часть, отправив серию сообщений и сделав паузу
между ними, как показано в листинге 17-10.

Имя файла: src/main.rs

        let (tx, mut rx) = trpl::channel();

        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("future"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            trpl::sleep(Duration::from_millis(500)).await;
        }

        while let Some(value) = rx.recv().await {
            println!("received '{value}'");
        }

Листинг 17-10: Отправка и получение нескольких сообщений по асинхронному 
               каналу и ожидание между каждым сообщением

Помимо отправки сообщений, нам нужно их получать. В данном случае, 
поскольку мы знаем, сколько сообщений поступает, мы могли бы сделать это 
вручную, вызвав rx.recv().await четыре раза. Однако в реальном мире мы 
обычно ожидаем неизвестное количество сообщений, поэтому нам нужно 
продолжать ждать, пока не будет установлено, что сообщений больше нет.

В листинге 16-10 мы использовали цикл for для обработки всех элементов, 
полученных из синхронного канала. Однако в Rust пока нет возможности 
написать цикл for для асинхронной последовательности элементов, поэтому 
нам нужно использовать цикл, с которым мы раньше не сталкивались: 
условный цикл while let. Это циклическая версия конструкции if let, 
которую мы видели в разделе «Краткий поток управления с if let и let else»
https://doc.rust-lang.org/stable/book/ch06-03-if-let.html
. 
Цикл будет выполняться до тех пор, пока заданный им шаблон продолжает соответствовать значению.

Вызов rx.recv создаёт будущий объект, который мы ожидаем. Среда 
выполнения приостанавливает будущий объект до его готовности. После 
получения сообщения будущий объект будет преобразован в Some(message) 
столько раз, сколько сообщений приходит. После закрытия канала, 
независимо от того, были ли получены какие-либо сообщения, будущий объект 
вместо этого преобразуется в None, что означает, что больше нет значений,
и поэтому нам следует прекратить опрос, то есть прекратить ожидание.

Цикл while let объединяет всё это. Если результат вызова rx.recv().await 
— Some(message), мы получаем доступ к сообщению и можем использовать его в
теле цикла, как и с if let. Если результат — None, цикл завершается. 
Каждый раз, когда петля цикл завершается, он снова достигает точки 
ожидания, поэтому среда выполнения снова приостанавливает его до получения
следующего сообщения.

Теперь код успешно отправляет и получает все сообщения. К сожалению, есть
ещё пара проблем. Во-первых, сообщения приходят не с интервалом в 
полсекунды, а все сразу, через 2 секунды (2000 миллисекунд) после запуска
программы. Во-вторых, эта программа никогда не завершается! Вместо этого 
она ждёт новых сообщений бесконечно. Вам придётся завершить её, 
нажав Ctrl+C.

Давайте начнём с того, что разберёмся, почему сообщения приходят сразу 
после полной задержки, а не с задержками между каждым из них. В пределах 
одного асинхронного блока порядок, в котором ключевые слова await 
появляются в коде, совпадает с порядком их выполнения при запуске 
программы.

В листинге 17-10 только один асинхронный блок, поэтому всё в нём 
выполняется линейно. Конкурентность по-прежнему отсутствует. Все вызовы 
tx.send выполняются вперемешку со всеми вызовами trpl::sleep и связанными
с ними точками ожидания. Только после этого цикл while let проходит все 
точки ожидания в вызовах recv.

Чтобы получить желаемое поведение, при котором задержка ожидания 
происходит между каждым сообщением, нам нужно поместить операции tx и rx
в отдельные асинхронные блоки, как показано в листинге 17-11. Тогда среда
выполнения сможет выполнить каждую из них отдельно с помощью trpl::join, 
как в примере с подсчётом. И снова, мы ожидаем результат вызова trpl::join,
а не отдельные фьючерсы. Если бы мы ожидали отдельные фьючерсы 
последовательно, мы бы просто вернулись к последовательному потоку — 
именно то, чего мы пытаемся избежать.

Имя файла: src/main.rs

        let tx_fut = async {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;

Листинг 17-11: Разделение отправки и получения на отдельные асинхронные 
               блоки и ожидание будущих событий для этих блоков

Благодаря обновленному коду в листинге 17-11 сообщения выводятся с 
интервалом в 500 миллисекунд, а не все сразу через 2 секунды.

Однако программа по-прежнему никогда не завершается из-за того, как цикл 
while let взаимодействует с trpl::join:
a) Future, возвращаемый из trpl::join, завершается только после завершения
    обоих переданных ему future-объектов.
b) Future tx завершается, как только оно завершает спящий режим после 
    отправки последнего сообщения в vals.
c) Future rx не завершится, пока не закончится цикл while let.
d) Цикл while let не завершится, пока ожидание rx.recv не вернет None.
e) Ожидание rx.recv вернет None только после закрытия другого конца канала.
f) Канал закроется только в том случае, если мы вызовем rx.close или 
    когда отправитель, tx, прервется.
j) Мы нигде не вызываем rx.close, и tx не будет отброшен, пока не 
    завершится самый внешний асинхронный блок, переданный в trpl::run.
k) Блок не может завершиться, поскольку он блокируется при завершении 
    trpl::join, что возвращает нас к началу этого списка.

Мы могли бы вручную закрыть rx, вызвав rx.close где-нибудь, но это не 
имеет особого смысла. Остановка после обработки произвольного количества 
сообщений приведёт к завершению программы, но мы можем пропустить 
сообщения. Нам нужен другой способ гарантировать, что tx будет удален до 
завершения функции.

Сейчас асинхронный блок, в который мы отправляем сообщения, заимствует 
только tx, поскольку отправка сообщения не требует владения. Но если бы 
мы могли переместить tx в этот асинхронный блок, он был бы удален по 
завершении этого блока. В разделе «Захват ссылок или перемещение владения»
https://doc.rust-lang.org/stable/book/ch13-01-closures.html#capturing-references-or-moving-ownership
главы 13 вы узнали, как использовать ключевое слово move с замыканиями, и,
как обсуждалось в разделе «Использование замыканий move с потоками» 
https://doc.rust-lang.org/stable/book/ch16-01-threads.html#using-move-closures-with-threads
главы 16, нам часто приходится перемещать данные в замыкания при работе с
потоками. Та же базовая динамика применима и к асинхронным блокам, поэтому
ключевое слово move работает с асинхронными блоками так же, как и
с замыканиями.

В листинге 17-12 мы меняем блок, используемый для отправки сообщений, с 
async на async move. При запуске этой версии кода он корректно завершает
работу после отправки и получения последнего сообщения.

Имя файла: src/main.rs

        let (tx, mut rx) = trpl::channel();

        let tx_fut = async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;

Этот асинхронный канал также является каналом с несколькими 
производителями, поэтому мы можем вызвать clone on tx, если хотим 
отправлять сообщения из нескольких будущих событий, как показано в 
листинге 17-13.

Имя файла: src/main.rs

        let (tx, mut rx) = trpl::channel();

        let tx1 = tx.clone();

        let tx1_fut = async move {
            let vals = vec![
                String::from("hi"),
                String::from("from"),
                String::from("the"),
                String::from("future"),
            ];

            for val in vals {
                tx1.send(val).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        let tx_fut = async move {
            let vals = vec![
                String::from("more"),
                String::from("messages"),
                String::from("for"),
                String::from("you"),
            ];

            for val in vals {
                tx.send(val).unwrap();
                trpl::sleep(Duration::from_millis(1500)).await;
            }
        };

        trpl::join3(tx1_fut, tx_fut, rx_fut).await;

Листинг 17-13: Использование нескольких производителей с асинхронными 
               блоками

Сначала мы клонируем tx, создавая tx1 вне первого асинхронного блока. Мы 
перемещаем tx1 в этот блок, как и раньше с tx. Затем, позже, мы перемещаем
исходный tx в новый асинхронный блок, откуда отправляем новые сообщения с 
чуть меньшей задержкой. Мы случайно помещаем этот новый асинхронный блок 
после асинхронного блока для получения сообщений, но он мог бы также идти
и перед ним. Ключевым моментом является порядок ожидания будущих событий,
а не порядок их создания.

Оба асинхронных блока для отправки сообщений должны быть асинхронными 
блоками перемещения, чтобы и tx, и tx1 были удалены после их завершения. 
В противном случае мы снова окажемся в том же бесконечном цикле, с 
которого начали. Наконец, мы переключаемся с trpl::join на trpl::join3 для
обработки дополнительного future-объекта.

Теперь мы видим все сообщения от обоих отправляющих фьючерсов, и поскольку
отправляющие фьючерсы используют немного разные задержки после отправки,
сообщения также принимаются с этими разными интервалами.

received 'hi'
received 'more'
received 'from'
received 'the'
received 'messages'
received 'future'
received 'for'
received 'you'

Это хорошее начало, но оно ограничивает нас всего несколькими фьючерсами:
двумя с join или тремя с join3. Посмотрим, как мы можем работать с 
большим количеством futures.
