Шаг 2.6: Запечатывание
=================

__Estimated time__: 1 day

В программировании «запечатывание» обычно означает, что некоторый API (в основном публичный) не может быть унаследован, расширен или реализован за пределами места его определения. Например, [запечатанный класс или интерфейс в Kotlin][1] не может быть унаследован или реализован за пределами библиотеки, где он определен. В [Rust] этот принцип может применяться к [трейтам][2].


## Traits

__Запечатанный trait__ — это __общедоступный__ trait, который __не может быть реализован вне места его определения__ (__module или crate__, в зависимости от видимости этого признака).
> ```rust
> // приватный модуль с именем private
> mod private {
>     pub trait Sealed {}   // трейт Sealed
>
>     // Реализация трейта Sealed для типа usize.
>     impl Sealed for usize {}
> }
>
> /// публичный трейт TheTrait наследующий от публичного трейта Sealed из приватного модуля с именем private
> /// модуль private не может быть экспортирован из текущего crate, это значит что трейт не может быть реализован вне текущего ctate
> pub trait TheTrait: private::Sealed {
>     // Ноль или более методов, которые пользователю разрешено вызывать.
>     fn ...();
>
>     // скрытие функции из документации, медод формально запрещено вызывать
>     #[doc(hidden)]
>     fn ...();
> }
>
> // Реализуйте трейт TheTrait для типа usize.
> impl TheTrait for usize {
>     /* ... */
> }
>
> ```
> Пустой private супертрейт `Sealed` не может быть использован нижестоящими крейтами, поэтому мы гарантируем, что реализации `Sealed` (и, следовательно, `TheTrait`) существуют только в текущем крейте.

Это наиболее распространенный способ запечатать trait. Стандартный текст можно полностью убрать, используя крейт [`sealed`], который предоставит удобный макрос для его генерации:

```rust
use sealed::sealed;

#[sealed]
pub trait TheTrait {}

#[sealed]
impl TheTrait for usize {}
```

Однако существуют альтернативные способы запечатать признак [с помощью сигнатуры его метода][5] или даже [запечатать его частично][6].

Главная цель защиты признака, конечно же, заключается в [обеспечении защиты от будущих угроз][7] для [API].

> Мы можем добавлять методы в `TheTrait` в релизе, не нарушающем обратную совместимость, даже если это обычно приводит к изменению совместимости для трейтов, которые не запечатаны. Также мы можем изменять сигнатуру методов, которые не задокументированы публично.

Важно отметить, что __запечатывание трейта полностью основано на__ обмане с правилами видимости (__использовании публичного [супертрейта][8]__ или типа, имя которого не является публично экспортируемым__), и поэтому не влияет на семантику системы типов (запечатанный публичный трейт — это просто обычный публичный трейт с точки зрения системы типов). Теоретически, запечатывание трейта должно влиять на его [когерентность][9], [ослабляя его строгость для вариантов использования, которые никогда не могут произойти с запечатанным трейтом][10]. Однако это потребовало бы специальной поддержки со стороны компилятора, что, похоже, [не произойдет в ближайшем будущем][11].


Для лучшего понимания свойств запечатывания, её конструкции и областей применения, ознакомьтесь со следующей информацией:
- [Rust API Guidelines: 10. Future proofing: Sealed traits protect against downstream implementations (C-SEALED)][3]
- [Predrag Gruevski: A definitive guide to sealed traits in Rust][4]
- [Jack Wrenn: Private Methods on a Public Trait][13]
- [Official `sealed` crate docs][`sealed`]

<h3>Полное руководство по закрытым свойствам (sealed traits) в Rust</h3>

Долгое время я думал, что «запечатанный трейт» в Rust — это единая концепция, реализуемая одним конкретным способом. Чтобы предотвратить реализацию ваших трейтов в последующих крейтах, вы делаете трейты запечатанными — и всё, конец истории. Я ошибался! Оказывается, существует множество способов запечатать трейты, образующих приятный спектр возможностей:

|Что|Вышестоящий код может использовать его в качестве привязки.|Вышестоящий код может вызывать его методы.|Вышестоящие типы могут его реализовывать.|
|---|----|----|---|
|pub trait|✅|✅|✅|
|supertrait sealed trait|✅|✅|❌|
|method signature sealed trait|✅|❌|❌|
|private trait|❌|❌|❌|

На самом деле, чуть позже мы увидим, что даже это не полная картина! Наш выбор может быть еще более детальным, чем то, что мы видим выше:

- Можно запретить вызов только подмножества методов трейта.
- Можно разрешить нижестоящему коду реализовывать трейт, одновременно запрещая этим реализациям переопределять некоторые методы трейта.

<h4>Что такое запечатанные признаки (sealed traits)?</h4>

Трейт считается закрытым, если его нельзя реализовать вне собственного крейта.

Почему это важно?

Добавление новых методов к трейту обычно приводит к серьёзным изменениям, нарушающим совместимость: все типы, реализующие этот трейт, также должны реализовывать новые методы. Но что, если мы хотим избежать необходимости выпуска новой основной версии?

Есть два способа обойти это.

Первый вариант — добавить реализацию по умолчанию для всех новых методов в трейте. Тогда любые типы, реализующие трейт, получат эту реализацию «бесплатно» и смогут заменить её своей собственной. Иногда это разумно, но не всегда. Например, может и не быть подходящей реализации по умолчанию, и использование todo!() в качестве реализации по умолчанию определённо вызовет вопросы.

Второй вариант требует некоторого обдумывания: при первоначальном добавлении трейта мы должны были сделать его запечатанным. Запечатанные трейты могут быть реализованы только типами в рамках текущего крейта. Поскольку никакие другие крейты не могут подвергнуться критическим изменениям, это изменение не является основным изменением семантического версионирования.

Хотя существует несколько способов запечатать тот или иной признак, все они основаны на одном и том же приёме.

<h4>Трюк для запечатывания трейтов</h4>

В общих чертах, хитрость с закрытием трейтов довольно проста: нужно сделать так, чтобы реализация trait требовала тип, доступный только внутри текущего crate. Crates, находящиеся ниже по цепочке, не смогут использовать этот тип, поэтому они не смогут реализовать trait. Готово!

На практике требуется некоторая тонкость. Rust не допускает утечки приватных типов в публичном API крейта:

```rust
trait PrivateTrait {}

pub trait PublicTrait : PrivateTrait {}
```
Произведено [playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2021&gist=c8a04e39ab23f400bbcb5d376372a6a2)

```
error[E0445]: private trait `PrivateTrait` in public interface
 --> src/lib.rs:3:1
  |
1 | trait PrivateTrait {}
  | ------------------ `PrivateTrait` declared as private
2 |
3 | pub trait PublicTrait : PrivateTrait {}
  | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ can't leak private trait
```

Чтобы избежать подобных ошибок, нам нужно убедиться, что все типы в API нашего трейта являются <b>публичными</b>.

Однако тип Rust может быть публичным, даже если его имя не является публичным. Это различие делает возможным использование запечатанных трейтов.

<h4>Закрепление признаков с помощью суперпризнака (Sealing traits with a supertrait)</h4>

Вместо использования приватного супертрейта, давайте воспользуемся публичным супертрейтом, имя которого не экспортируется в открытый доступ:

```rust
mod private {
    pub trait Sealed {}
}

pub trait SealedTrait : private::Sealed {
    fn method(&self);
}
```

Реализовать `SealedTrait` для типа в том же крейте очень просто. 

1. Сначала реализуйте `private::Sealed` для этого типа
2. Затем реализуйте `SealedTrait` обычным способом:

```rust
pub struct TypeThatImplsSealed;

impl private::Sealed for TypeThatImplsSealed {}

impl SealedTrait for TypeThatImplsSealed {
    fn method(&self) {}
}
```

Нижестоящие модули этого сделать не могут! Хотя сам `Sealed` является публичным, он определяется в частном модуле и никогда не экспортируется повторно. Это означает, что тип является публичным, но его имя — приватным.

Обращение к `private::Sealed` из нижестоящего крейта приводит к ошибкам:

```rust
struct DownstreamType {}

// ERROR: module `private` is private
impl upstream::private::Sealed for DownstreamType {}
```

Попытка реализовать `SealedTrait` непосредственно в библиотеке, созданной на основе исходного кода, также терпит неудачу:

```rust
struct DownstreamType {}

// ERROR: the trait bound `DownstreamType: upstream::private::Sealed` is not satisfied
impl upstream::SealedTrait for DownstreamType {
    fn method(&self) {}
}
```
Причина проблем в том что для `DownstreamType` не реализован трейт `upstream::private::Sealed`.

Однако такое закрытие трейта не препятствует вызову его методов в нижестоящем коде. Следующий код в нижестоящем крейте работает отлично:
```rust
fn use_sealed(value: impl upstream::SealedTrait) {
    value.method()
}
```
Вот тут-то и появляется другой способ запечатать поступающие traits.

<h4>Запечатывание traits с помощью сигнатур методов.</h4>

Иногда `trait` должно быть `pub`, но мы хотим предотвратить вызов его методов нижестоящими crates.

Мы воспользуемся той же идеей "неименуемых типов", но на этот раз применимой к аргументам метода, а не к супертрейту:

```rust
mod private {
    pub struct Token;
}

pub trait SealedTrait {
    fn method(&self, _: private::Token);
}
```

`private::Token` — это структура типа `unit`, и, будучи `zero-sized type` (`ZST`), она не создаст никаких накладных расходов на производительность. Для создания значения структуры `unit` достаточно указать её имя, поэтому код, имеющий возможность указать имя для private::Token, может вызвать метод трейта следующим образом: [playground](https://play.rust-lang.org/?version=stable&mode=debug&edition=2021&gist=34eb425ec87dddc1ea34dbc4a6984597)

```rust
pub struct TypeThatImplsSealed;

impl SealedTrait for TypeThatImplsSealed {
    fn method(&self, _: private::Token) {
        // impl here
    }
}
```

Между тем, нижний код может видеть и называть трейт и его метод, но не может реализовать трейт или вызвать метод:

```rust
struct DownstreamType {}

impl upstream::SealedTrait for DownstreamType {
    // ERROR: module `private` is private
    fn method(&self, token: upstream::private::Token) {}
}


fn call_method(value: impl upstream::SealedTrait) {
    // ERROR: module `private` is private
    let token = upstream::private::Token;
    value.method(token);
}
```

Пока хотя бы один обязательный метод трейта принимает аргумент с неименованным типом, трейт считается закрытым и не может быть реализован последующими библиотеками.

В последнем предложении есть две хитрые вспомогательные фразы: «по крайней мере один» и «необходимый метод». Давайте рассмотрим каждую из них по очереди.

<h3>Что означает «запечатывание» в программировании в широком смысле?</h3>

В программировании термин «запечатывание» (`sealing`) означает ограничение возможности расширения или изменения программного компонента внешним кодом.

В широком смысле это механизм контроля иерархии, который запрещает другим программистам наследоваться от вашего класса или реализовывать ваш интерфейс за пределами строго определенной области (обычно — текущего модуля или библиотеки).

Вот основные аспекты «запечатывания» в разных парадигмах:

<h4>1. Запечатывание в объектно-ориентированном программировании (ООП)</h4>

В таких языках, как C#, Kotlin или Java, запечатывание используется для остановки цепочки наследования.

- Механизм: Ключевые слова sealed (Kotlin/Java) или sealed / final (C#).
- Цель: Гарантировать, что поведение класса не будет переопределено. Это упрощает поддержку кода, так как автор точно знает все возможные подтипы своего класса.
- Пример: Если вы создаете класс CreditCardPayment, вы можете «запечатать» его, чтобы никто не мог создать «поддельный» подкласс, который меняет логику списания средств.

<h4>2. Запечатывание типов (Алгебраические типы данных)</h4>

В функциональных и современных системных языках (Swift, Scala, а также Java 17+) «запечатанный» интерфейс или класс позволяет компилятору знать все возможные варианты реализации.

- Преимущество: Это включает проверку полноты (`exhaustiveness checking`). Если вы используете `match` или `switch` по запечатанному типу, компилятор выдаст ошибку, если вы забыли обработать один из вариантов. В Rust эту роль выполняют `enum`.

<h4>3. Запечатывание в контексте Rust (`Sealed Traits`)</h4>

Хотя в Rust нет ключевого слова sealed, программисты используют этот шаблон (паттерн), чтобы запретить пользователям библиотеки реализовывать определенный трейт для своих типов.

- Как это работает: Трейт делается зависимым от другого (скрытого в приватном модуле) трейта.
- Зачем: Это позволяет автору библиотеки добавлять новые методы в трейт, не ломая код пользователей (так как пользователи всё равно не могли его реализовать сами).

<h4>Почему «запечатывание» — это хорошо?</h4>

- Безопасность (`Security`): Гарантия того, что критически важный код не будет подменен или расширен непредсказуемым образом.
- Оптимизация (`Performance`): Компилятор может применять более агрессивные оптимизации (например, `devirtualization`), так как он точно знает, что новых наследников у типа не появится.
- Предсказуемость API: Пользователь библиотеки получает четкие границы использования инструмента, что снижает риск ошибок.

<h4>Когда НЕ стоит запечатывать?</h4>

Если вы разрабатываете фреймворк, который по своей сути должен расширяться пользователями (например, система плагинов или базовые UI-компоненты), запечатывание будет излишним и вредным ограничением.

<h4>Итог:</h4>
Запечатывание — это способ сказать: «Этот компонент завершен и должен использоваться именно так, как я задумал, без вмешательства в его структуру».

<h3>Что такое «запечатывание трейтов» в [Rust]? Когда это полезно?</h3>

«Запечатывание трейтов» (`Sealed Traits`) в Rust — это архитектурный паттерн, который позволяет объявить pub трейт (доступный извне), но при этом запретить пользователям вашей библиотеки реализовывать его для своих типов.

В Rust это стандартный способ контроля стабильности API и обеспечения безопасности системы типов.

<h4>Как это работает?</h4>

Механизм основан на том, что в Rust нельзя реализовать трейт, если у него есть «супертрейт» (`super-trait`), к которому у вас нет доступа.

1. Создается приватный модуль (обычно с именем `private` или `sealed`).
2. В нем определяется «скрытый» трейт.
3. Ваш публичный трейт делается зависимым от этого скрытого трейта.

Пример реализации:

```rust
// Приватный модуль, который не экспортируется из библиотеки
mod private {
    // Этот трейт нельзя увидеть или реализовать вне этого файла
    pub trait Sealed {}
}

// Публичный трейт, который "запечатан"
// Наследуется от приватного трейта
pub trait MyPublicTrait: private::Sealed {
    fn do_something(&self);
}

// Мы можем реализовать его для наших типов внутри библиотеки
pub struct MyType;

// реализация для SuperTrate -> private::Sealed
impl private::Sealed for MyType {}

// релизация для прозводного Trate -> MyPublicTrait
impl MyPublicTrait for MyType {
    fn do_something(&self) { println!("Работает!"); }
}
```

Пользователь библиотеки увидит `MyPublicTrait`, сможет вызывать его методы, но не сможет написать `impl MyPublicTrait for UserType`, так как он не может реализовать обязательный `private::Sealed`.

<h4>Когда это полезно?</h4>

1. Гарантия обратной совместимости

Если трейт «открыт», добавление нового метода в него — это `breaking change` (разрушающее изменение), так как все реализации пользователя перестанут компилироваться. Если трейт запечатан, вы можете добавлять новые методы в любое время, не боясь сломать код пользователей (все добавления только в библиотеке разработчика).

2. Ограничение области применения

Когда трейт имеет смысл только для строго определенного набора типов (например, только для примитивных чисел или только для внутренних структур драйвера). Запечатывание предотвращает «мусорные» реализации для типов, которые не соответствуют логике вашей системы.

3. Безопасность и инварианты

В системном программировании (например, работа с регистрами процессора или DMA), где неправильная реализация трейта пользователем может привести к `Undefined Behavior`. Запечатывание гарантирует, что только проверенный вами код реализует эти критические интерфейсы.

4. Упрощение оптимизаций

Зная, что новых реализаций трейта не появится, компилятор (и вы как автор кода) можете делать более смелые предположения о том, как ведет себя система, что потенциально улучшает производительность.

<h4>Итог</h4>

Используйте `Sealed Traits`, если вы разрабатываете библиотеку и хотите предоставить пользователям интерфейс для использования, но не для расширения. Это один из самых мощных инструментов для поддержания стабильности крупных экосистем в Rust.

<h3>Какие ограничения имеет механизм изоляции трейтов в [Rust]? Что он мог бы обеспечить, если бы поддерживался компилятором?</h3>

Механизм «запечатывания» трейтов в Rust на текущий момент является не встроенной функцией компилятора, а архитектурным хаком (паттерном), использующим правила видимости. Это накладывает на него ряд существенных ограничений.

<h4>Текущие ограничения механизма (паттерна `Sealed Traits``)</h4>

1. Бинарный характер «всё или ничего»: Вы не можете запретить реализацию трейта выборочно. Трейт либо открыт для всех, либо запечатан для всех внешних пользователей. Нельзя разрешить реализацию только для определенных «доверенных» крейтов без использования нестабильных функций (вроде pub(restricted)).
2. Проблемы с документацией: В сгенерированной документации `rustdoc` запечатанный трейт всё равно показывает супертрейт-заглушку (например, `impl MyTrait for MyType where Self: private::Sealed`). Это сбивает с толку пользователей, так как они видят требование, которое физически не могут выполнить.
3. Неявность: Поскольку ключевого слова `sealed` не существует, новый разработчик в проекте может не сразу понять, почему он не может реализовать трейт. Это «социальное» ограничение, требующее дополнительного комментирования кода.
4. Сложность при наследовании: Если вы запечатываете один трейт в цепочке иерархии, вам часто приходится запечатывать и все зависимые от него трейты, что приводит к раздуванию приватных модулей.

<h4>Что мог бы обеспечить встроенный механизм (если бы он поддерживался компилятором)?</h4>

Если бы в Rust ввели полноценное ключевое слово `sealed trait`, это дало бы следующие преимущества:

1. Истинная проверка полноты (Exhaustiveness Checking)

Сейчас компилятор не знает, что реализаций трейта всего три. Если бы трейт был запечатан на уровне языка, компилятор позволил бы делать так:

```rust
// Гипотетический синтаксис будущего
match dyn_value_of_sealed_trait {
    MyType1 => { ... },
    MyType2 => { ... },
    // Ветка _ => unreachable!() больше не нужна!
}
```
Это сделало бы динамическую диспетчеризацию (`dyn Trait`) такой же безопасной и удобной, как работу с enum.

2. Девиртуализация (`Devirtualization`)

Компилятор мог бы гарантированно заменять вызовы через таблицу виртуальных методов (`vtable`) прямыми вызовами функций или инлайнингом, так как он точно знал бы, что новых реализаций не появится в рантайме (например, через динамическую загрузку библиотек). Это бы существенно сократило разрыв в производительности между `dyn Trait` и статикой.

3. Улучшенная специализация

Запечатывание помогло бы решить конфликты при специализации (`Specialization`). Если компилятор знает полный список типов, реализующих трейт, ему проще разрешить ситуации, когда несколько реализаций перекрывают друг друга.

4. Чистый API и документация

Вместо хаков с `mod private`, разработчики могли бы просто помечать трейт как pub sealed trait. Документация бы четко отображала: «Этот трейт доступен для использования, но закрыт для реализации».

<h4>Резюме</h4>

На данный момент запечатывание в Rust — это защита автора библиотеки от ошибок пользователя. Если бы оно стало частью языка, оно превратилось бы в инструмент оптимизации производительности и улучшения эргономики кода, сближая возможности трейтов и перечислений (`enum`).
