Шаг 2.3: Ограничение поведения, а не данных.
==================================

__Estimated time__: 1 day

Часто, когда мы хотим абстрагироваться от какого-либо типа или поведения в [Rust], мы начинаем с этого:
```rust
struct UserService {
    repo: UserRepo,
}
```
к этому:
```rust
struct UserService<R: UserRepo> {
    repo: R,
}
```

Здесь мы указываем привязку `R: UserRepo`, поскольку хотим ограничить типы в поле `repo` для реализации поведения `UserRepo`.

Однако такое ограничение непосредственно на тип приводит к так называемому «загрязнению границ трейтов»: нам приходится повторять это ограничение в каждой отдельной реализации, даже в тех, которые никак не связаны с поведением `UserRepo`.
```rust
struct UserService<R: UserRepo> {
    repo: R,
}

impl<R> Display for UserService<R>
where
    R: Display + UserRepo, // <- We are not interested in UserRepo here,
{                          //    all we need is just Display.
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "UserService with repo {}", self.repo)
    }
}
```

В сложной кодовой базе подобное загрязнение, возникающее из-за множества различных типов данных, в какой-то момент может превратиться в настоящий кошмар.

Решение этой проблемы заключается в понимании того, что __трейт представляет собой определенное поведение__, и, в действительности, __нам это поведение нужно только тогда, когда мы его объявляем__. Объявление типа не содержит ничего о поведении, оно полностью посвящено данным. __Поведение проявляется в функциях и методах__. Поэтому давайте просто будем ожидать определенного поведения, когда оно нам действительно понадобится:
```rust
struct UserService<R> {
    repo: R,
}

// Ожидайте отображения (Expect Display) при выражении поведения отображения.
impl<R: Display> Display for UserService<R> {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "UserService with repo {}", self.repo)
    }
}

// Ожидайте UserRepo, когда мы будем описывать фактическое поведение UserService,
// которое работает с Users.
impl<R: UserRepo> UserService<R> {
    fn activate(&self, user: User) {
        // Changing User state in UserRepo...
    }
}
```

Размещение ограничений трейтов на блоках `impl`, методах и функциях, а не на типах, _уменьшает загрязнение трейтами_, _снижает [связность][1] частей кода_ и _делает обобщенный код более чистым, понятным и эргономичным_.



## Снять ненужные ограничения

В качестве более общего правила: __следует стараться максимально расширять ограничения трейтов__ (особенно в библиотечном коде), поскольку это увеличивает разнообразие вариантов использования типа.


Иногда для этого необходимо отказаться от использования `#[derive]`, поскольку это может привести к ненужной привязке к трейту. Например:
```rust
#[derive(Clone)]
struct Loader<K, V> {
    state: Arc<Mutex<State<K, V>>>,
}

struct My;

let loader: Loader<My, My> = ..;
let copy = loader.clone(); // compile error as `My` doesn't impl `Clone`
```
Это происходит потому, что `#[derive(Clone)]` применяет ограничения `K: Clone` и `V: Clone` в производном коде, несмотря на то, что они совершенно не нужны, поскольку [`Arc` всегда реализует `Clone`][2] (также рассмотрите ограничение `T: ?Sized` в [linked implementation][2], которое снимает неявное ограничение `T: Sized`, поэтому позволяет использовать `Arc::clone()` даже для [unsized types][3]).

Предоставляя реализованный вручную код, мы можем без проблем клонировать значения типа `Loader<My, My>`:
```rust
struct Loader<K, V> {
    state: Arc<Mutex<State<K, V>>>,
}

// Ручная реализация используется для того, чтобы избежать применения ненужных ограничений Clone.
impl<K, V> Clone for Loader<K, V> {
    fn clone(&self) -> Self {
        Self {
            state: self.state.clone(),
        }
    }
}

let loader: Loader<My, My> = ..;
let copy = loader.clone(); // it compiles now!
```

<h3>Какие проблемы создают ограничения трейтов в [Rust] при их размещении на определении типа?</h3>

Размещение ограничений трейтов (`trait bounds`) непосредственно в определении структуры (`struct MyStruct<T: Trait>`) в Rust считается антипаттерном. Идиоматичным подходом является перенос ограничений на блоки `impl`.

Вот основные проблемы, которые создает такое размещение:

<h4>1. Избыточность и «шум» в коде (Duplication)</h4>

Если вы ограничите `T` в определении структуры, вам придется повторять это ограничение в каждом блоке `impl`, в каждой функции, принимающей эту структуру, и в каждом вложенном типе.

- Результат: Код становится перегруженным и трудным для чтения. Если ограничение изменится, его придется исправлять в десятках мест.

<h4>2. Ограничение гибкости (Negative Impact on Generics)<h4>

Часто структура может быть полезна даже для типов, которые не реализуют основной трейт.

- Пример: Вы определили `struct Container<T: Display>`. Теперь вы не можете просто хранить в нем T, который не реализует Display, даже если вы не собираетесь его печатать.
- Последствия: Это ломает композицию типов. Вы не сможете использовать методы структуры, не требующие этого трейта (например, конструкторы или геттеры), если T не соответствует жесткому критерию.

<h4>3. Проблемы с обратной совместимостью</h4>

Если вы решите убрать или изменить ограничение в определении типа, это будет разрушающим изменением (`breaking change`) для всех пользователей вашей библиотеки. Перенос ограничений на конкретные методы позволяет добавлять функциональность постепенно, не ломая старый код.

<h4>4. Сложность при реализации трейтов</h4>

При реализации других трейтов (например, `Serialize` из `Serde`) наличие ограничений в корневой структуре может сбивать с толку макросы и авто-реализации, требуя ручного прописывания сложных связей.

<h4>Как делать правильно (Best Practice 2026)</h4>

Вместо того чтобы ограничивать саму структуру, ограничивайте методы:
```rust
// Плохо: ограничение на структуре
struct Buffer<T: Copy> { 
    data: T 
}

// Хорошо: структура свободна
struct Buffer<T> {
    data: T
}

// Ограничиваем только там, где это необходимо
impl<T: Copy> Buffer<T> {
    fn duplicate(&self) -> (T, T) {
        (self.data, self.data)
    }
}

// Методы, не требующие Copy, доступны всем
impl<T> Buffer<T> {
    fn new(data: T) -> Self {
        Self { data }
    }
}
```

<h4>Исключения (Когда это оправдано)</h4>

Ограничения на структуре допустимы только в двух редких случаях:

- Связанные типы (`Associated Types`): Когда структура использует типы, определенные внутри трейта (например, `T::Item`).
- Трейты-маркеры времени компиляции: Если структура физически не может существовать без этого трейта (крайне редко в прикладном коде).

Итог: Храните определение структуры наиболее «чистыми» от блокировки. Это сделает ваш API более гибким, а рефакторинг — менее болезненным. Подробнее в Rust API Guidelines.

<h3>Почему размещение ограничений на трейты в блоках `impl` предпочтительнее?</h3>

В Rust перенос ограничений (`bounds`) с определения структуры в блоки `impl` считается «золотым стандартом» проектирования API. Это делает код более гибким, поддерживаемым и чистым.

Вот основные причины, почему это предпочтительнее:

<h4>1. Гибкость использования структуры</h4>

Если ограничение стоит на самой структуре (`struct Wrapper<T: Display>`), вы не сможете создать экземпляр этой структуры с типом, который не реализует `Display`.

- Преимущество `impl`: Вы можете создать `Wrapper<T>` для любого `T`. Ограничения появятся только тогда, когда вы захотите вызвать методы, специфичные для `Display`. Это позволяет использовать структуру в контекстах, о которых вы даже не задумывались (например, просто как контейнер для хранения или передачи данных).

<h4>2. Упрощение рефакторинга и эволюция API</h4>

Если вы решите изменить или добавить ограничение в определении структуры, это будет разрушающим изменением (`breaking change`) для всех пользователей вашего кода.

- Преимущество `impl`: Вы можете добавлять новые блоки impl с новыми ограничениями, не ломая существующий код. Это позволяет вашему типу «обрастать» функциональностью постепенно.

<h4>3. Устранение дублирования кода</h4>

Если ограничение указано в определении структуры, компилятор Rust требует, чтобы вы повторяли это ограничение в каждом блоке impl для этой структуры.

- Преимущество `impl`: Вы пишете ограничение только там, где оно реально нужно. Если у вас есть 10 методов, и только 2 из них требуют `Serialize`, вам не нужно заставлять остальные 8 методов знать об этом трейте.

<h4>4. Поддержка частичной реализации</h4>

Это позволяет реализовать базовую логику для всех типов, а специфическую — только для некоторых.

```rust
struct Container<T>(T);

// Базовый метод доступен для ВСЕХ типов
impl<T> Container<T> {
    fn new(val: T) -> Self { Self(val) }
}

// Метод печати доступен ТОЛЬКО для типов с Display
impl<T: std::fmt::Display> Container<T> {
    fn print(&self) { println!("{}", self.0); }
}
```

<h4>5. Совместимость с макросами и дериавацией</h4>

Многие процедурные макросы (например, `#[derive(Serialize)]` в Serde) работают гораздо лучше и предсказуемее, когда структуры не имеют лишних ограничений. Это избавляет от необходимости вручную настраивать атрибуты для корректной генерации кода.

<h4>Когда ограничения в структуре ВСЁ ЖЕ нужны?</h4>

Существует только один основной сценарий, где это оправдано: если структура использует ассоциированные типы трейта.
```rust
// Здесь ограничение необходимо, чтобы компилятор знал о существовании T::Item
struct Processor<T: Iterator> {
    current_item: T::Item,
}
```

<h4>Итог:</h4>

Правило большого пальца (Rule of Thumb): Оставляйте структуру максимально «голой». Накладывайте ограничения на методы в блоках `impl` ровно в тот момент, когда вам нужно вызвать функции этого трейта. Это делает ваш код идиоматичным и удобным для расширения. Официальная рекомендация [Rust API Guidelines](https://rust-lang.github.io/api-guidelines/about.html).
