Шаг 2.5: Исчерпывание
======================

__Estimated time__: 1 day


Проверка полноты в [сопоставлении с образцом][1] — очень полезный инструмент, позволяющий выявлять определенные ошибки на этапе компиляции, проверяя, были ли учтены и рассмотрены все комбинации значений в исходном коде. При правильном применении она повышает качество [бесстрашного рефакторинга][2] исходного кода, исключая возможность незаметного проникновения ошибок типа «забыл изменить» в кодовую базу при ее расширении.


## Enums

Наиболее каноническим и знаковым примером проверки исчерпываемости является использование перечисления в выражении `match`. Суть здесь в том, чтобы __[опустить][5] использование [`_` (шаблон подстановки)][4] или привязок «соответствует чему угодно»__, поскольку такие выражения `match` не сломаются во время компиляции при добавлении чего-либо нового.

Например, это очень плохой код:
```rust
fn grant_permissions(role: &Role) -> Permissions {
    match role {
        Role::Reporter => Permissions::Read,
        Role::Developer => Permissions::Read & Permissions::Edit,
        _ => Permissions::All, // anybody else is administrator 
    }
}
```
Если по какой-либо причине будет добавлен новый объект `Role::Guest`, то с очень высокой вероятностью этот код не будет соответствующим образом изменен, что приведет к возникновению уязвимости безопасности, поскольку любому гостю будет предоставлено разрешение `Permissions::All`. Это происходит главным образом потому, что сам код никак не сигнализирует о необходимости его пересмотра.


Благодаря использованию принципа исчерпывающего поиска, код можно изменить таким образом, __чтобы он ломался на этапе компиляции при добавлении нового варианта `Role`__:
```rust
fn grant_permissions(role: &Role) -> Permissions {
    match role {
        Role::Reporter => Permissions::Read,
        Role::Developer => Permissions::Read & Permissions::Edit,
        Role::Admin => Permissions::All, 
    }
}
```
```

note: `Role` defined here
  --> src/lib.rs:2:5
```

## Structs

В то время как исчерпывающая детализация перечислений является довольно очевидной идеей из-за широкого использования выражений `match` в обычном коде, исчерпывающая детализация структур, с другой стороны, не является таковой, хотя и столь же полезна. Исчерпывающая детализация структур достигается путем __использования [деструктуризации][6] без [`..` синтаксиса (игнорирование нескольких полей)][7]__.

Например, имея следующий код:
```rust
struct Address {
    country: Country,
    city: City,
    street: Street,
    zip: Zip,
}

impl fmt::Display for Address {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        writeln!(f, "{}", self.country)?;
        writeln!(f, "{}", self.city)?;
        writeln!(f, "{}", self.street)?;
        write!(f, "{}", self.zip)
    }
}
```

Очень легко забыть изменить реализацию `Display` при добавлении нового поля `state`.


Таким образом, изменение кода с помощью __исчерпывающей деструктуризации позволяет избежать такой незаметной ошибки, возникающей на этапе компиляции__:

```rust
impl fmt::Display for Address {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        let Self {
            country,
            city,
            street,
            zip,
        } = self;
        writeln!(f, "{country}")?;
        writeln!(f, "{city}")?;
        writeln!(f, "{street}")?;
        write!(f, "{zip}")
    }
}
```

## `#[non_exhaustive]`

До настоящего времени было показано, __как проверка на исчерпывающий характер кода может обеспечить перспективность пользовательского кода__ (того, который использует API определенного типа, а не объявляет его), __заставляя его ломаться всякий раз, когда используемый [API] расширяется__ и требует пересмотра.


__Интересно, что атрибут `#[non_exhaustive]`__, __служит той же самой цели [обеспечения защиты от устаревания][12]__ исходного кода, но совершенно противоположным образом: __он используется в библиотечном коде__ (том, который объявляет [API] какого-либо типа для использования) __для сохранения обратной совместимости, чтобы избежать нарушения работы пользовательского кода при расширении используемого [API]__.


> Внутри определяющего крейта параметр `non_exhaustive` не оказывает никакого эффекта.

> За пределами определяющей библиотеки типы, аннотированные `non_exhaustive`, имеют ограничения, обеспечивающие обратную совместимость при добавлении новых полей или вариантов.

> 
> Non-exhaustive типы не могут быть сконструированы вне определяющего крейта:

> - Non-exhaustive варианты (варианты `struct` или `enum`) нельзя создать с помощью `StructExpression` (в том числе с использованием синтаксиса функционального обновления).

> - могут быть созданы экземпляры `enum`.

> При сопоставлении с non-exhaustive типов, выходящих за рамки определяющей библиотеки, существуют ограничения:
> - При сопоставлении с шаблоном для non-exhaustive варианта (`struct` или `enum`) необходимо использовать `StructPattern`, который должен включать `...`. Видимость конструктора варианта кортежа снижается до `min($vis, pub(crate))`.


> - При сопоставлении с шаблоном по non-exhaustive `enum` сопоставление с вариантом не учитывается при определении исчерпываемости вариантов.

> Также запрещено использовать non-exhaustive типы из чужих crates.

> Non-exhaustive типы всегда считаются обитаемыми в нижележащих crates.

Despite being opposite qualities, both exhaustivity and non-exhaustivity are intended for [future-proofing][12] a codebase, thus cannot be applied blindly everywhere, but rather wisely, where it may really has sense. That's why it's __very important__ to understand their __use-cases and implicability__ very well.

Несмотря на то, что exhaustivity и non-exhaustivity подходы являются противоположными качествами, они предназначены для обеспечения устойчивости кода в будущем [12], поэтому их нельзя применять слепо повсюду, а следует использовать разумно там, где это действительно имеет смысл. Вот почему очень важно хорошо понимать их сценарии использования и применимость.

Чтобы лучше понять назначение, структуру, ограничения и варианты использования атрибута `#[non_exhaustive]`, ознакомьтесь со следующей информацией:
- [Rust Reference: 7.6. The `non_exhaustive` attribute][9]
- [Rust RFC 2008: `non_exhaustive`][10]
- [Turreta: Using `#[non_exhaustive]` for Non-exhaustive Rust Structs][11]

<h3>Как может быть полезна проверка полноты в коде [Rust] для перечислений и структур? Когда её следует использовать, а когда нет?</h3>

В Rust проверка полноты (`Exhaustiveness Checking`) — это механизм компилятора, который гарантирует, что при обработке данных (обычно через match) были учтены все возможные варианты.

<h4>Как это полезно для перечислений (`Enums`)</h4>

Для перечислений проверка полноты является «ангелом-хранителем» разработчика:

- Безопасный рефакторинг: Если вы добавите новый вариант в enum (например, добавите `Status::Archived` к `Active` и `Inactive`), компилятор мгновенно подсветит все блоки match по всей программе, которые нужно обновить. Это исключает баги, когда вы забыли обработать новый кейс в каком-то редком модуле.
- Логическая целостность: Вы можете быть уверены, что программа не попадет в состояние «неопределенности», так как ветка «по умолчанию» (`_ => ...`) заставляет вас либо обработать всё, либо явно признать, что остальные случаи вам не важны.

<h4>Как это полезно для структур (`Structs`)</h4>

Для структур проверка полноты проявляется при деструктуризации:

- Контроль полей: Если вы добавите новое поле в структуру, код, который разбирает её через `let Struct { a, b } = s ;`, перестанет компилироваться, требуя явно указать новое поле или использовать `...`
- Гарантия инициализации: Компилятор не позволит создать экземпляр структуры, не указав значения для всех её полей.

<h4>Когда её СЛЕДУЕТ использовать</h4>

1. Бизнес-логика и конечные автоматы: Если enum представляет состояния процесса (например, этапы оплаты или статусы заказа), проверка полноты обязательна. Вы должны явно знать, что происходит на каждом этапе.
2. Публичные API библиотек: При проектировании библиотек использование исчерпывающего `match` гарантирует, что пользователь вашей библиотеки не пропустит важные изменения в новых версиях.

<h4>Когда её использовать НЕ СЛЕДУЕТ (или стоит ограничить)</h4>

1. Типы, которые будут часто расширяться (`#[non_exhaustive]`):

При создании библиотек для `enum` и `struct`, которые могут получить новые поля в будущем, крайне рекомендуется использовать атрибут `#[non_exhaustive]`. Это заставляет пользователей извне всегда добавлять ветку `_` в `match`, что предотвращает поломку их кода при обновлении вашей библиотеки.
2. Прототипирование: Если вы только набрасываете архитектуру, использование заглушки `_ => todo!()` позволяет двигаться быстрее, откладывая детальную реализацию на потом.
3. Огромные перечисления: Если в enum десятки вариантов, а вам интересны только два, использование проверки полноты для каждого случая создаст слишком много «шума» в коде. В таких ситуациях ветка по умолчанию оправдана.

<h4>Резюме</h4>

Проверка полноты — это способ превратить ошибки выполнения (логические пропуски) в ошибки компиляции. Используйте её как основной инструмент проектирования, но применяйте `#[non_exhaustive]` для публичных типов, чтобы сохранить возможность расширения API без боли для пользователей.

<h3>Как работает атрибут #[non_exhaustive] в [Rust]? В каких случаях он используется? Когда его следует использовать, а когда нет?</h3>

Атрибут `#[non_exhaustive]` (введен в Rust 1.40) — это инструмент обеспечения обратной совместимости. Он сообщает компилятору и пользователям вашего кода, что тип (перечисление или структура) может получить новые варианты или поля в будущем.

<h4>Как работает `#[non_exhaustive]`</h4>

Этот атрибут накладывает ограничения на то, как сторонний код (вне вашего крейта) может взаимодействовать с типом:

1. Для `enum`: Запрещает использовать «исчерпывающий» match без ветки «по умолчанию» (_). Если пользователь не добавит _ => ..., код не скомпилируется.
2. Для `struct`: Запрещает создание экземпляра структуры через литерал (например, `MyStruct { a, b }`) и её деструктуризацию вне вашего крейта. Создать такую структуру можно будет только через ваши конструкторы (например, `MyStruct::new()`).

<h4>В каких случаях он используется</h4>

1. Расширяемые перечисления (`Enums`)

Если вы создаете enum с ошибками или статусами, вы почти наверняка захотите добавить новые варианты в будущем. Без этого атрибута добавление нового варианта — это `breaking change` (разрушающее изменение), которое сломает код всех ваших пользователей.

```rust
#[non_exhaustive]
pub enum Error {
    NotFound,
    PermissionDenied,
    // В версии 2.0 мы добавим Timeout, и это ничего не сломает!
}
```

2. Эволюция структур (`Structs`)

Когда вы хотите иметь возможность добавлять новые поля в структуру, не заставляя пользователей переписывать каждый вызов инициализации.

<h4>Когда его СЛЕДУЕТ использовать</h4>

- В публичных API библиотек: Это «золотой стандарт» для типов ошибок, конфигураций и любых перечислений, которые логически могут расширяться .
- Для конфигурационных структур: Чтобы добавление новой настройки не требовало правок во всех местах, где эта структура создается вручную.
- При работе с внешними данными: Например, если вы описываете API стороннего сервиса, который может добавить новые поля в ответ в любой момент.

<h4>Когда его использовать НЕ СЛЕДУЕТ</h4>

1. Внутри одного крейта (Private API): Атрибут не действует внутри того же модуля или крейта, где определен тип. Там вы всегда видите полную картину, и проверка полноты (`exhaustiveness check`) должна работать на 100%.
2. Для логически завершенных типов: `Если` enum представляет собой фундаментальную математическую или логическую сущность, которая никогда не изменится.
    - Пример: `enum Direction { North, South, East, West }` или `enum Option<T>`. Здесь расширение невозможно или бессмысленно.
3. Когда вы хотите форсировать обработку всех вариантов: Если для вашей бизнес-логики критично, чтобы пользователь обязательно отреагировал на каждый возможный вариант (и вы готовы ломать его код при обновлениях ради безопасности).

<h4>Резюме</h4>

В современном Rust `#[non_exhaustive]` — это способ сказать пользователю: «Я оставляю за собой право развивать этот тип. Пожалуйста, всегда предусматривай вариант 'что-то еще' в своих match». Это делает экосистему более стабильной и менее хрупкой при обновлении зависимостей.
