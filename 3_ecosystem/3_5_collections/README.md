## Итераторы

> Итераторы широко используются в идиоматическом коде Rust, поэтому стоит с ними ознакомиться.

В то время как коллекция представляет собой полный набор данных, итератор — это способ итерации по её элементам.

> Итератор имеет метод [`next`][7], который при вызове возвращает `Option<Item>`. [`next`][7] будет возвращать `Some(Item)` до тех пор, пока есть элементы, и как только все они будут исчерпаны, вернет `None`, указывая на завершение итерации. Отдельные итераторы могут возобновить итерацию, поэтому повторный вызов [`next`][7] может в какой-то момент снова начать возвращать `Some(Item)`.

>
> Итераторы также являются составными, и их часто объединяют в цепочки для выполнения более сложных видов обработки.

В [Rust] существует три способа итерации по коллекции:
- Функция `iter()` перебирает заимствованные элементы (`&T`), поэтому используется для операций чтения с коллекцией.
- Функция `iter_mut()` выполняет итерацию по _изменяемо заимствованным_ элементам (`&mut T`), поэтому используется, когда требуется изменение элементов на месте.
- Функция `into_iter()` перебирает элементы, находящиеся в собственности (`T`), поэтому используется, когда требуется преобразование всей коллекции и/или перемещение элементов.

Важно помнить, __что итераторы (и их адаптеры) являются ленивыми__. [`Итератор`] ничего не делает, если не вызван его метод [`next()`][7]. Это свойство приводит к следующему: __итераторы не обязательно должны быть конечными__. Поэтому, если вам нужна своего рода бесконечная коллекция (например, бесконечная [последовательность Фибоначчи][8]), реализация с помощью [`Итератора` — это подходящий вариант, поскольку каждый новый элемент будет вычисляться лениво по запросу.

[`Iterator`] поставляется с множеством мощных и полезных [адаптеров][9] в библиотеке `std`, что делает их очень компонуемыми и удобными в использовании. Если возможностей `std` недостаточно для ваших нужд, рассмотрите возможность использования крейта [`itertools`], который предоставляет больше нетривиальных адаптеров.

## Неизменяемые коллекции

[Неизменяемые коллекции][10] (также известные как «постоянные структуры данных») — это коллекции, которые сохраняют интерфейс и поведение своих изменяемых аналогов, но имеют другую внутреннюю реализацию, которая __позволяет каждому фрагменту кода работать со своей собственной копией всей коллекции, не беспокоясь о случайном изменении элементов для других__. Ключевой особенностью является неявная дедупликация данных. Это неизбежно происходит за счет производительности, поэтому неизменяемые коллекции имеют [другие гарантии производительности][11], чем изменяемые.

В экосистеме [Rust] есть crates [`im`] и [`rpds`], которые предоставляют неизменяемые реализации для некоторых коллекций.

## Совместно используемые коллекции (Concurrent collections)

Когда необходимо работать с одной и той же коллекцией из нескольких потоков, наиболее распространенный и очевидный способ — это использовать для этого примитив синхронизации (например, `Arc<RwLock<VecDeque<T>>>`). Однако это _слишком плохо_ работает при интенсивном использовании коллекции. Именно поэтому существуют параллельные коллекции: они _позволяют использовать коллекцию из нескольких потоков без явной синхронизации_ и _обеспечивают эффективный механизм синхронизации внутри_ (обычно, используя алгоритмы без блокировок).

В экосистеме [Rust] есть крейты [`crossbeam`] и [`lockfree`], предоставляющие эффективные реализации без блокировок для некоторых коллекций, обычно используемых в параллельном контексте. Также рассмотрите крейты [`flurry`] и [`chashmap`] для совместной реализации [хэш-карты][`HashMap`].

Чтобы лучше понять природу, структуру и мотивацию создания параллельных коллекций, ознакомьтесь со следующими материалами:

### Что такое коллекция? Что такое итератор? Чем они отличаются? Как они используются? Какие ограничения есть у каждого из них?

1. #### Что такое Коллекция (Collection)?

__Коллекция__ — это структура данных, которая реально владеет набором значений и хранит их в памяти (обычно в куче/heap).

- Примеры: Vec<T>, HashMap<K, V>, BTreeMap<K, V>, String.
- Цель: Хранение, организация и быстрый доступ к данным.
- Ограничения:
    - Память: Потребляет место в куче.
    - Владение: Когда коллекция выходит из области видимости, она уничтожает все свои элементы (вызывает drop).

2. #### Что такое Итератор (Iterator)?

__Итератор__ — это «умный указатель» или процесс, который позволяет перебирать элементы последовательности один за другим. В Rust итераторы ленивы: они не делают ничего, пока вы не попросите следующее значение (.next()).

- Пример: my_vec.iter(), (0..100).filter(|x| x % 2 == 0).
- Цель: Обработка, фильтрация и трансформация данных без создания промежуточных копий в памяти.
- Ограничения:
    - Одноразовость: Большинство итераторов «потребляются» при использовании. После завершения цикла итератор пуст.
    - Отсутствие владения: Итератор обычно просто заимствует данные из коллекции (хранит ссылку), поэтому он не может «пережить» саму коллекцию.

3. #### Главные отличия

|Характеристика|Коллекция (напр. Vec)|Итератор|
|--------------|---------------------|--------|
|Хранение|Хранит данные физически.|Не хранит данные (вычисляет или ссылается).|
|Вычисления|Данные уже готовы.|Ленивые: вычисляются при обращении.|
|Размер|Фиксирован в памяти.|Может быть бесконечным (напр. (0..)).|
|Стоимость|Высокая (аллокация в куче).|Zero-cost (обычно оптимизируется в цикл).|

4. #### Как они используются вместе?

Типичный цикл жизни данных в Rust выглядит так:

- Коллекция: У вас есть исходные данные (Vec).
- Итератор: Вы создаете итератор (.iter()), чтобы отфильтровать или изменить их.
- Коллекция: Вы собираете результат обратно в новую коллекцию (.collect()).

Пример:

```rust
let numbers = vec![1, 2, 3, 4, 5]; // Коллекция

let doubled_evens: Vec<i32> = numbers
    .iter()                // Создаем итератор по ссылкам
    .filter(|&x| x % 2 == 0) // Ленивая фильтрация
    .map(|&x| x * 2)       // Ленивое умножение
    .collect();            // Собираем в новую коллекцию
```

5. #### Ограничения

- Коллекции: Требуют управления памятью. Вставка в середину Vec может быть медленной (O(n)).
- Итераторы: Вы не можете произвольно прыгнуть в середину итератора (нужно вызвать .next() n раз). Также итератор блокирует коллекцию (вы не можете менять Vec, пока по нему открыт iter()), чтобы избежать [ошибок доступа](https://www.google.com/url?sa=i&source=web&rct=j&url=https://doc.rust-lang.org/nomicon/aliasing.html&ved=2ahUKEwiBz97C2MSSAxU1ExAIHcUvCSkQy_kOegYIAQgTEAQ&opi=89978449&cd&psig=AOvVaw33btpfIaRL_vMFnyV5R5OO&ust=1770461322228000).

__Важный совет__: Всегда старайтесь выполнять как можно больше работы через итераторы перед тем, как вызывать .collect(). Это позволяет компилятору Rust применить инлайнинг и превратить ваш сложный код в один максимально быстрый цикл на языке ассемблера.

### Что такое неизменяемые коллекции? Как они работают? Почему не стоит использовать их постоянно? Когда имеет смысл их использовать?

В Rust термин «неизменяемые коллекции» обычно относится не к стандартным Vec или HashMap (которые становятся неизменяемыми просто при отсутствии mut), а к персистентным структурам данных (Persistent Data Structures).

Наиболее популярной библиотекой для этого является [im](https://docs.rs/im/latest/im/) (или её более быстрая версия [im-rc](https://docs.rs/im-rc/latest/im_rc/index.html)).

1. #### Что это такое и как они работают?

В отличие от стандартного Vec, где любое изменение перезаписывает старые данные, неизменяемая (персистентная) коллекция при «изменении» создает новую версию самой себя, сохраняя при этом старую.

- _Структурное разделение (Structural Sharing)_: Это ключ к их работе. Вместо полного копирования данных, новая коллекция ссылается на узлы старой коллекции.
- _Деревья (HAMT/B-Trees)_: Под капотом они обычно реализованы как деревья. При добавлении элемента создается не вся копия массива, а только новая ветка дерева (путь от корня до нового элемента), в то время как остальные ветки остаются общими для обеих версий.

2. #### Почему не стоит использовать их постоянно?

Несмотря на «магию», у них есть существенная цена:

- Производительность (CPU): Поиск и вставка в дерево всегда медленнее (O(log n)), чем в плотный массив Vec (O(1)) или HashMap.
- Промахи кэша (Cache Misses): Современные процессоры любят непрерывные блоки памяти (как в Vec). Деревья разбросаны по куче, что заставляет процессор чаще ждать данных из оперативной памяти.
- Счетчики ссылок (Arc/Rc): Для разделения данных используются счетчики ссылок. Их постоянное обновление при каждом «изменении» создает накладные расходы, особенно в многопоточной среде.
- Сложность: API таких коллекций часто сложнее, и их труднее интегрировать с библиотеками, ожидающими стандартные слайсы &[T].

3. #### Когда имеет смысл их использовать?

- Функциональное программирование: Если вы пишете код в функциональном стиле, где данные не меняются (immutability), а создаются новые состояния.
- Undo/Redo и версионность: Идеально для приложений, где нужно хранить историю изменений (например, текстовые редакторы или графические пакеты). - Вы просто сохраняете «корни» деревьев для каждой версии — это дешево.
- Безопасный Shared State в многопоточности: Вы можете передать одну и ту же коллекцию в 10 потоков. Если один поток «изменит» её, он получит свою копию, а остальные продолжат работать со старой версией без всяких блокировок (Mutex).
- Сложные алгоритмы на графах/деревьях: Где нужно постоянно «пробовать» разные пути развития данных, не теряя текущую точку.

__Резюме__

Используйте стандартные Vec, HashMap и BTreeMap в 95% случаев. Переходите на [im](https://docs.rs/im/latest/im/), только если вам критически важна персистентность (возможность держать в памяти несколько версий данных одновременно) или вы хотите избежать сложных блокировок в многопоточном коде.

### Что такое коллекции одновременного доступа (concurrent)? Как они работают? Почему они лучше, чем явная синхронизация для обычной коллекции?

В Rust concurrent коллекции (потокобезопасные коллекции) — это структуры данных, специально спроектированные для одновременного доступа из нескольких потоков без необходимости оборачивать их в тяжеловесные блокировки вроде Mutex<Vec<T>>.

Наиболее популярными реализациями являются библиотеки [dashmap](https://docs.rs/dashmap/latest/dashmap/) (аналог HashMap) и [crossbeam-skiplist](https://docs.rs/crossbeam-skiplist/latest/crossbeam_skiplist/) (аналог BTreeMap).

1. #### Как они работают?

Вместо того чтобы блокировать всю коллекцию целиком при любом изменении, concurrent коллекции используют более тонкие механизмы:

- Шардирование (Sharding): Коллекция внутри разбивается на множество независимых сегментов (шардов). Если поток записывает данные в первый шард, другой поток может одновременно читать или писать во второй. Это минимизирует «конфликты» (contention).
- Lock-free алгоритмы: Некоторые коллекции используют атомарные инструкции процессора (CAS — Compare-And-Swap) вместо мьютексов. Это позволяет изменять указатели в памяти без остановки других потоков.
- Управление памятью (Epoch-based Reclamation): Чтобы безопасно удалить элемент, который другой поток может в этот момент читать, используются сложные схемы очистки памяти (например, из крейта crossbeam-epoch).

2. #### Почему они лучше, чем явная синхронизация (Mutex/RwLock)?

Когда вы используете _Mutex<HashMap<K, V>>_, возникает «бутылочное горлышко»:

- Масштабируемость: С ростом количества ядер процессора производительность Mutex падает, так как все потоки выстраиваются в очередь к одной «двери». Concurrent коллекции позволяют ядрам работать параллельно.
- Мертвые блокировки (Deadlocks): При ручном управлении мьютексами легко заблокировать два ресурса в разном порядке и остановить программу навсегда. Внутренняя логика concurrent коллекций обычно защищена от этого.
- Задержки (Tail Latency): Mutex может заставить поток «уснуть», что приведет к долгому ожиданию. Lock-free коллекции стараются минимизировать такие паузы.

3. #### Сравнение подходов

|Характеристика|Mutex<HashMap>|DashMap (Concurrent)|
|--------------|--------------|--------------------|
|Параллелизм|Нулевой (один поток за раз)|Высокий (много потоков одновременно)|
|Простота|Очень просто|Требует понимания API (ссылки-гарды)|
|Чтение|Блокирует запись|Не блокирует другие чтения|
|Накладные расходы|Минимальный при 1 потоке|Выше (из-за шардирования и атомиков)|

4. #### Когда использовать?

- Используйте Mutex/RwLock, если коллекция маленькая, обновляется редко или если вам нужно выполнить сложную атомарную операцию над несколькими элементами сразу.
- Используйте Concurrent коллекции, если у вас высоконагруженный сервис (например, кэш в веб-сервере), где сотни потоков постоянно читают и пишут данные.

__Пример (DashMap)__:

```rust
use dashmap::DashMap;
use std::sync::Arc;

let shared_map = Arc::new(DashMap::new());

// Можем клонировать Arc и раздавать в сотни потоков
// Каждый поток сможет делать .insert() или .get() без явного .lock()
shared_map.insert("key", "value");
```

__Итог__: Concurrent коллекции — это инструмент для высокопроизводительного параллелизма. Они обменивают небольшое количество лишней памяти на колоссальный выигрыш в скорости при работе на многоядерных системах.
